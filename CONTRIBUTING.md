# Contributing

Bake is being rebuilt from scratch to follow the redesign. This file holds the architecture rules every change must respect. When a rule can be checked by a test, the test is named next to it; new rules are added here.

## Tool and blog are separate

This repository contains only the tool: the CLI, the Markdown pipeline, the built-in themes and the optional component kit. Posts, components, custom themes and site settings live in the blog's own repository. Bake never assumes a particular blog. `examples/blog/` is the only blog in this repository: it holds the syntax article that lists every syntax item, serves as the source of the tutorial, and is the integration test fixture. Unit tests that need other blogs, such as error cases, create them in temporary directories.

## Planned layout

The layout grows task by task. Today `src/cli.js`, `src/report.js`, `src/fragments.js`, `src/urls.js`, `src/escape.js`, `src/content-types.js`, `src/bundle/`, `src/config/`, `src/markdown/`, `src/build/`, `src/render/`, `src/components/`, `src/kit/`, `src/copy/`, `src/chat/`, `src/dev/`, `src/themes/essay/` and `src/themes/bento/` exist. `src/config/` reads `bake.config.js`, front matter and `preamble.sty`, `src/markdown/` parses the article body into the article structure and writes mdast trees back to Markdown for copying, `src/render/` typesets math, highlights code, reads and converts images and turns Markdown nodes into HTML, `src/fragments.js` gives the ids of sidenotes and reference entries and turns an id into the fragment of an address and back, `src/urls.js` builds the addresses of articles and files and parses the addresses that links point to, `src/escape.js` escapes the text that Bake writes into HTML and XML by hand, `src/content-types.js` gives the content type of a published file, `src/bundle/` holds the Vite configuration, the browser build and the public modules that the themes, the components and the AI chat share, `src/components/` reads the components of a blog, checks their parameters and bundles them with the browser runtime, `src/kit/` holds `bake/kit`, the optional controls and plot parts for components, `src/copy/` turns a selection on a published page into Markdown for the clipboard, `src/chat/` is the AI chat that readers open on published pages, `src/build/` reads the blog, resolves the links between articles, compiles the themes, renders the pages, the homepage and the 404 page, writes the RSS feed and the sitemap, draws the share images and writes `dist/`, `src/dev/` serves the pages for `bake dev` and updates them on save, and `src/themes/essay/` and `src/themes/bento/` are the essay and bento themes.

The modules that run in the browser import no built-in module of Node, with or without the `node:` prefix: the files of the themes, the AI chat module `src/chat/entry.js`, the component runtime `src/components/runtime.js` and the public modules `bake/copy`, `bake/fragments`, `bake/math` and `bake/kit`, together with every module they import.

## Themes interpret, they never add syntax

The set of things an article can write (heading levels, blocks, width levels `body`, `wide` and `page`, front matter fields) is defined by Bake alone. A theme receives the parsed article and decides how to lay it out; it cannot add attributes, blocks or front matter fields. An attribute no theme knows is a build error, and so is an attribute without the value its syntax requires, such as `:::aside{title}` or a heading with `{id}`. Adding syntax means changing Bake's syntax table and stating what it means in every theme.

## The article structure

The article structure is the interface between Bake and the themes. Bake builds it in two steps, because links and embeds refer to other articles. `readArticle(file, source, errors, { folder, preamble, url, components })` in `src/markdown/article.js` parses one `index.md`, typesets its math and reads its images; it is asynchronous for that reason. `folder` is `{ path, files }` of the article folder, which images are resolved against, `preamble` holds the definitions read from `preamble.sty` by `src/config/preamble.js`, `url` is the address of the article, `/YYYY-MM/slug/`, and `components` is the map from component name to component that `readComponents` in `src/components/read.js` returns, which the component blocks of the article are checked against. When every article has been read, `indexPages(pages)` in `src/build/links.js` indexes them by address, `link(index, errors)` on each article checks its links and `:::embed` blocks against that index, where an anchor with an invalid percent-encoding such as `#%ZZ` is an error, and `structure()` returns the article structure. `link` reports its problems and those of the following `structure()` call into `errors` and replaces the result of an earlier `link`, so the two steps can run again on a parsed article when other articles change. The front matter is read separately by `src/config/front-matter.js`. Every `html` value is an HTML fragment that a theme inserts unchanged.

| Field | Contents |
|---|---|
| `source` | The text of the `index.md` as read, front matter included. Every `line` and `endLine` in the structure counts lines of this text from 1, so line `n` is `source.split('\n')[n - 1]`. |
| `intro` | The blocks before the first `##` heading. |
| `sections` | One entry per `##` heading: `id`, `number` (`01`, `02` and so on), `title` (HTML), `text` (plain text), `toc` (the title for the table of contents, from `{toc="…"}` or the heading text), `width` (`body`, `wide`, `page` or undefined), `line` and `endLine` (the first and last line of the heading), `recap` (HTML, when the section has a `:::recap` before its first `###` heading), `titleSidenotes` and `recapSidenotes` (the numbers of the sidenotes that the heading and the recap refer to, each once, in the order in which they first refer to them, empty when there are none), `blocks` and `subsections`. |
| `subsections` | One entry per `###` heading in the section: `id`, `title`, `text`, `toc`, `line`, `endLine`, `recap`, `titleSidenotes` and `recapSidenotes`. |
| `toc` | The table of contents: for each section `id`, `number`, `title`, `recap` and `children`, and for each `###` heading in `children` its `id`, `title` and `recap`. The titles are plain text. |
| `sidenotes` | The footnotes, numbered by their first reference: `number`, `id` (`sidenote-1`), `label` (the label as written, such as `gemm` for `[^gemm]`), `line` and `endLine` (the first and last line of the definition), `html` and `sidenotes` (the numbers of the sidenotes that the definition refers to, in the same form). |
| `references` | The entries of `:::references`, numbered by their first citation: `key`, `number`, `id` (`reference-key`) and `html`. Entries the article never cites follow the cited ones and have no `number`. |
| `previews` | One entry per target of the internal links on the page, including links and citations inside embedded content, for the preview card: `target` (the address of the article followed by the decoded anchor, such as `/2026-10/rope/#angles`), `href` (the address relative to the page), `kind`, `article` (the title of the target article), `number`, `title` and `html`. For a `reference` entry, `number` is the citation number of the entry in its article (undefined for an entry that is never cited) and `html` is the entry. For a `section` entry, `number` is the number of the section that holds the target, such as `3` or `3.2` for its second `###` heading, undefined before the first `##` heading and for a whole article; `title` is the HTML of the target heading, or of the heading of the section that holds any other target, undefined for a whole article; `html` holds at most three blocks after a target heading or at the start of a whole article, ending before the next heading, the target paragraph, the display formula of a target equation, or the content of a target sidenote. |
| `words` | The length of the article: every Chinese character and every other word of the text and inline code counts as one. Code blocks, math, sidenotes and embedded content are not counted. |
| `images` | The images that the build converts to WebP: `source` (the path in the article folder), `path` (the published path), `width`, `lossless` and `keepSource`, which is true when the original file is named by the address of a link, by an address in raw HTML, from `srcset` or from an attribute that `html-url-attributes` lists as a URL, such as `src`, `href` or `poster`, or by the value of a string parameter of a component, so that it is published too. The addresses are read like an image address and the parameter values like a `file` parameter, as the paragraph on `folderFile` below describes. Images published unchanged are copied with the other files of the folder. |
| `image` | The published path in the article folder of the first image in reading order, with sidenotes read where they are referenced and the captions of components read as text, so a homepage card shows an image of a component caption and never a component: the WebP path for a converted image and the original path for an image published unchanged. Undefined when the article has no image. |
| `components` | The names of the components the page uses, sorted: the components of the article and of the content it embeds. A preview card shows no component, so previews add none. |
| `glyphs` | When the page has math: an HTML fragment with a hidden `<svg>` that holds the glyph paths of every formula in the article and of the formulas in its embeds and previews. Formulas refer to these paths, so the page includes the fragment once, together with the MathJax styles. MathJax names each path after the font, the variant and the character, so the paths of formulas from different articles combine into one fragment. |

A block has `type`, `line`, `endLine`, `html` and `sidenotes`, the numbers of the sidenotes that the block refers to, each once, in the order in which it first refers to them, so a theme places sidenotes without reading the HTML. The type is the mdast node type (`paragraph`, `heading`, `list`, `blockquote`, `code`, `math`, `table`, `html`, `thematicBreak`), `figure` for an image on its own line, the name of a built-in block (`aside`, `fold`, `references`, `example`, `list-table`, `embed`) or `component`. A block wrapped in `:::{width=…}` has `width`. A block whose natural width Bake knows at build time has `naturalWidth`, a CSS length that the theme or page script compares with the column to place the block automatically: the formula width in `ex` for display math, the longest line in `ch` for code, with East Asian wide characters counted as two, and the written width for a figure or a component whose width is set in pixels. A figure without a size or with a percentage size has no `naturalWidth` and stays inside the text column, however wide its image file is. Tables have no `naturalWidth`; the page measures them. A component always has `width` or `naturalWidth`, so the page never measures it. A paragraph that ends with `^name` and a heading have `id`. A `###` or deeper heading also has `depth`, `title`, `text` and `toc`. A component has `name`, `attributes` (the attributes as written) and `params` (every declared parameter, converted to its type, with the defaults filled in), and `width` set from its `width` attribute or its `layout.width`, see Components below. An example whose result holds components or figures with a pixel width has `resultWidths`, their widths in reading order without repeats: the width level of each component (`body` for a component with a percentage width) and the pixel width of each component or figure with one, such as `['560px', 'body']`. Such an example also has `naturalWidth`, the largest of those pixel widths, and `width`, `page` or `wide` when a component in it has that level. Headings inside other blocks do not start sections, and a `:::recap` inside another block stays in that block's HTML as `<div class="recap">`.

Embedded and previewed content comes from another article, so Bake renders it differently from the article's own content: headings, paragraphs, reference list items and raw HTML elements have no `id`, equations keep their numbers but lose their ids, sidenote numbers are left out, and links to anchors of the source article, citations, equation references and relative image addresses point into the source article. A link to an anchor of the source article becomes an internal link, and a citation has `data-target` with the address of its entry, so the preview card shows the entry of the source article. A preview shows the caption of a component as `<div class="component-caption">` in place of the component. Embedded content shows a component with its frame, as its source article does, and the value of each `file` parameter points into the source article, such as `../../2026-10/rope/grid.json`, so the component loads the file that the source article publishes.

`folderFile(path, files)` in `src/config/rules.js` decides whether a value names a file of the article folder, for images, component parameters, `keepSource` and the front matter fields `preview`, `cover` and `page`. It normalizes the path, rejects a path that starts with `/` or leaves the folder, and looks the result up in the files of the folder. The front matter uses its first step, `folderPath(path)`, to report a path outside the folder separately from a file that does not exist. Image addresses, link addresses and the addresses in raw HTML are URLs, so before the lookup Bake rejects an address with a scheme, drops the query and the fragment and percent-decodes the rest: `![](a%231.png)` names the file `a#1.png`, and `![](a#1.png)` names `a`. Component parameters and the front matter fields are paths and are looked up as written: `points=a#1.png` and `cover: a#1.png` name the file `a#1.png`.

Every address that Bake builds from a file path, such as the `src` of an image, a `file` parameter of a component, the preview of a homepage card, the stylesheets and scripts in the `assets` prop of a page and the absolute addresses in the site files, is URL-encoded segment by segment with `encodePath` in `src/urls.js`, so a file name with `#`, `?`, `%` or a space, or a theme whose folder name holds one, gives an address that names that file.

## Themes

A theme is a folder with five entry files. `page.jsx` default-exports a SolidJS component that returns the whole `<html>` element of an article page; `home.jsx` default-exports a SolidJS component that returns the whole `<html>` element of the homepage; `not-found.jsx` default-exports a SolidJS component that returns the whole `<html>` element of the 404 page; `client.jsx` is the page script of these pages and imports the theme's stylesheets, fonts and other files; `theme.css` is the stylesheet that plain HTML pages can link to get the theme's fonts, colours and dark mode. Every theme needs `page.jsx` and `client.jsx`. The site theme, `theme` in `bake.config.js`, also needs `home.jsx`, `not-found.jsx` and `theme.css`; a theme that only articles choose does not. The built-in themes live in `src/themes/`. A blog adds a theme with a folder `themes/<name>/`, and replaces single files of a built-in theme with files of the same relative path in a folder of the same name, such as `themes/essay/header.jsx`; every relative import inside a theme folder is looked up in the blog's folder first and in the built-in folder second. This covers the imports of JavaScript files that start with `./` or `../`, every `@import` line of a stylesheet, also of a stylesheet that is itself pulled in by an `@import` line, and the `url()` addresses of stylesheets; in a stylesheet an address without `./`, such as `@import url(styles/c.css)`, is relative too, and when neither folder holds the file, Vite resolves the address itself, for example as the package stylesheet `lxgw-wenkai-webfont/lxgwwenkai-regular.css`. Vite inlines `@import` lines with a quoted address or with `url()` with or without quotes. Vite reads the keyword only in lowercase, so a plugin in `src/build/theme.js` writes the keyword of every `@import` line in lowercase in each stylesheet of a theme folder that Vite compiles itself, such as `theme.css` or a stylesheet that `client.jsx` imports, which makes `@IMPORT` work there; a stylesheet that is only pulled in by an `@import` line is inlined as written and needs the keyword in lowercase. A theme imports `solid-js` from Bake, so a blog does not install it. The theme compiler also resolves two public modules of Bake for every theme, as described in "Vite builds" below: `bake/copy`, described in "What a theme writes for copying", and `bake/fragments`, `src/fragments.js`, which has no Node imports. `sidenoteId(number)` and `referenceId(key)` return the ids that Bake gives sidenote `number` and the reference entry `key`, such as `sidenote-1` and `reference-key`. `fragmentOf(id)` returns the fragment that links to an id, with the id percent-encoded, such as `#eq%3Achain` for `eq:chain`. `idOfFragment(hash)` returns the id that a fragment such as `location.hash` names, or null when the fragment is empty or has an invalid percent-encoding, and `elementOfFragment(document, hash)` returns the element with that id, or null. The fragments in the links that Bake writes, such as those of sidenote numbers, citations, equation references and internal links, come from `fragmentOf`, and the essay theme uses these functions for its heading links, its table of contents, its homepage chips and the targets of in-page links and citation cards.

`src/build/theme.js` compiles the site theme and each theme that a published article uses with Vite and `vite-plugin-solid`. The site theme is compiled even when the blog has no articles, because the homepage and the 404 page are always written. `page.jsx`, and for the site theme `home.jsx` and `not-found.jsx`, are compiled together for the server into one module that exports `render` for article pages, `renderHome` for the homepage and `renderNotFound` for the 404 page, and are rendered to static HTML with Solid's `renderToString`, without hydration. `client.jsx` is compiled into the page script, an ES module that a page loads with `<script type="module">`, in one build of `browserBuild`, described in "Vite builds". A module that the page script, a module it imports or `bake/copy` loads with a dynamic `import()` is a separate chunk, which the browser fetches when the import runs, together with the stylesheet of the CSS that the chunk imports. The CSS that the page script imports, directly or through the chunks it imports statically, becomes the stylesheets that the page links. The page script and its stylesheet are named after the theme, such as `assets/essay-[hash].js` and `assets/essay-[hash].css`, and the chunk of a dynamic import after the imported file, such as `assets/lazy-[hash].js` for `./lazy.js`; the scripts, the stylesheets and the fonts and images they refer to are written to `dist/assets/` under names that contain a content hash. The browser runs a module script after it has parsed the document and before `DOMContentLoaded`, in the order of the script elements, so the page script finds the whole page when it starts. A script that has to run before the first paint, such as the script that applies the stored reader settings in the essay theme, is written inline in the head. A browser fetches a module script in CORS mode, and a page opened from a `file://` address has an opaque origin, so the browser runs none of the module scripts of such a page, while its stylesheets and images load. `src/build/theme.js` looks up the relative imports of a theme folder in a Vite alias that matches every address and resolves it with `customResolver`, because Vite resolves the `@import` lines and `url()` addresses of stylesheets with its aliases and its own resolver and without calling plugin `resolveId` hooks; the alias returns the file it finds in a theme folder and leaves every other address to Vite. Vite 8 deprecates the `customResolver` option of an alias and Vite 9 removes it, and a `resolveId` hook cannot take its place, because Vite resolves the `@import` lines and `url()` addresses of stylesheets with only its alias plugin and its own resolver, so this lookup has to be replaced when Bake moves to Vite 9. The deprecation warning does not show, because the builds log nothing. The `theme.css` of the site theme is compiled in a separate Vite build to `dist/_bake/theme.css`; its fonts and images are written to `dist/assets/` like those of `client.jsx`, and its `url()` addresses are relative to `dist/_bake/`. A theme that cannot be compiled is reported at the file and position of the error, an article that the theme throws on is reported at the article, and a homepage or a 404 page that the site theme throws on is reported at the theme folder.

The site files are written by `src/build/site-files.js` and `src/build/site.js`, and every address in them is absolute, built from `url` in `bake.config.js` with a slash added at its end, so `https://x.github.io/bake` gives `https://x.github.io/bake/2026-10/rope/`. `articleEntry(article, config)` in `src/build/entries.js` builds the metadata of one published article once: `title`, `summary`, `date`, `tags` (a list, empty when not set), `category` (the category object from `bake.config.js`, or undefined), `draft`, `url` (the address of the article, such as `/2026-10/rope/`), `path` (the same address relative to the site root, such as `2026-10/rope/`), `link` (the absolute address) and `preview` and `image` (the addresses of the preview file and of the first image relative to the site root, URL-encoded, or undefined). The article pages, the homepage, the 404 page, the feed, the sitemap, the catalog of the AI chat and the share images read these entries, and `newestFirst` in the same file sorts them in the order of the homepage. Drafts never appear in the site files, also in `bake dev`, where drafts have pages.

| `dist/404.html` | The 404 page, which GitHub Pages serves at every address without a file. |

The channel has the site title, the address of the homepage, `description` from `bake.config.js` or the site title when it is not set, and the language. The feed has no build time, so the same blog always gives the same file. |
| `dist/sitemap.xml` | A sitemap with one `<loc>` for the homepage and for each published article and plain HTML page. |
| `dist/og/YYYY-MM/slug-hash.png` | The share image of each published Markdown article that is not a draft, described in "Share images" below. A cover in JPEG, GIF or WebP keeps its format and gets the extension `.jpg`, `.gif` or `.webp`. |
| `dist/_bake/articles.json` | The catalog of the AI chat, described in "AI chat" below. |
| `dist/_bake/preamble.json` | The macro definitions of `preamble.sty` as a JSON list of TeX strings, which the AI chat loads before it typesets the first formula of an answer. |
| `dist/YYYY-MM/slug/index.md` | The `index.md` of each published Markdown article, unchanged, so that the AI chat can read the source of any article. |
| `dist/_bake/theme.css` | The compiled `theme.css` of the site theme. A plain HTML page links it with `<link rel="stylesheet" href="../../_bake/theme.css">`, which works in `bake dev` and at any address the site is served from; the absolute form `/_bake/theme.css` works only when the site is served at the root of its domain. The page is still published byte for byte. |

A file in `public/` that would be written to one of these addresses, or to any address in `dist/_bake/` or `dist/og/` or to a file the themes or the components write to `dist/assets/`, is reported as a conflict.

### Share images

`bake build` publishes one share image for every published Markdown article that is not a draft, and the essay and bento themes name it in the `og:image` tags of the article page. Plain HTML pages are published byte for byte, so no tag could refer to an image, and they get none. `src/build/share-images.js` plans and draws the images, and `src/build/share-card.js` holds the HTML template of the card.

When the front matter has `cover`, the cover becomes the share image at `og/YYYY-MM/slug-hash.ext`, where `hash` is the first 12 hexadecimal digits of the SHA-256 of the cover file. The cover must be a PNG, JPEG, GIF, WebP, AVIF or SVG image. Bake reads its format and size with sharp, and the format sharp detects decides the rest, whatever the file name says: a PNG, JPEG, GIF or WebP cover is published unchanged with the extension `.png`, `.jpg`, `.gif` or `.webp` and its MIME type in `og:image:type`, and an SVG or AVIF cover, which social networks do not show, is converted by sharp to a PNG of the same size. A cover sharp cannot read is reported at the `cover` field, in `bake dev` too.

Otherwise Bake draws a 1200 by 630 pixel PNG card and publishes it at `og/YYYY-MM/slug-hash.png`. The card has a vertical strip on the left in the category colour, or in `--accent` when the article has no category, a line with the site title and the category name, the title in bold, the summary below it, and on the right the first frame of the article's `preview` in a 16:9 frame. Without a preview the text takes the whole width. The card page links the compiled `theme.css` of the site theme with `data-theme="light"` on `<html>`, so it uses the fonts and the light colours of the site theme, and it uses these CSS variables of that stylesheet: `--bg`, `--ink`, `--ink-2`, `--ink-3`, `--accent`, `--line`, `--surface-2` and `--font-heading`. A site theme that does not define them gets a card with the browser's default colours and font.

The cards are drawn in Chromium through Playwright. `bake build` launches one browser only when at least one card has to be drawn, and draws the cards in four pages at a time. Each page loads the card from an address that only exists inside the browser, and Playwright answers every request from memory: the card, the files of the site theme and the files of the article folder. Every other request is refused, so drawing a card needs no network. The page imports the preview module, calls its default export with the empty element of the frame, checks that it returns `start` and `stop` like the homepage does, waits for the fonts and two animation frames, and takes the screenshot; `start` is never called. A preview that throws, fails to load, returns something else or does not finish within 10 seconds is reported at the `preview` field of the front matter. When Chromium cannot be launched, the build reports one error at the first article that needs a card, with Playwright's reason and the command `npx playwright install chromium`. Like every other error, these errors leave `dist/` unchanged. Bake plans a card for every article without errors of its own and draws the cards also when other articles or files have errors, so one run reports a throwing preview together with every other problem.

The hash in the name of a card covers every input of the drawing: the card template, the Playwright version, the site language and title, the category name and colour, the title, the summary, the path of the preview, the compiled `theme.css` of the site theme, which names its font files by their content hash, and, when the article has a preview, the path and content of every file in the article folder except `index.md`, so a change to any module that the preview imports gives a new name. When `dist/` already holds a file with the name of a card, `bake build` copies that file into the new `dist/` and does not draw the card again, so a build in which no card changed does not launch Chromium. Apart from these cards, the only cache is the bundle of the AI chat in the temporary directory of the system, described in "AI chat" below.

`createSite(root, { shareImages: true })` plans the share images, and only `bake build` sets it. `bake dev` draws no share images, so its pages have no `og:image` tags.

### What a theme writes for bake dev

`bake dev` updates an open page without reloading it when only the article body changed. A theme supports this with three attributes and one event, and the same HTML is published by `bake build`:

| Part | Meaning |
|---|---|
| `data-region="name"` | An element whose content comes from the article body, such as the article text, the table of contents or the word count. Each name appears once in the HTML that the theme renders. |
| `data-line="12"` | An element inside a region that shows one part of the article structure, with the `line` of that part: a block, a heading or a sidenote. |
| `bake:content` | The event that `bake dev` dispatches on `document` after it has replaced the content of the regions. |

After a save, the page script of `bake dev` loads the new HTML of the page. When the new page differs from the old one only inside regions, it updates every element with that `data-region` value, including copies that page scripts made, and dispatches `bake:content`. It compares the old and the new region node by node and replaces only the nodes that changed, descending into an element whose tag and attributes stayed the same, except a component frame, which is kept or replaced as a whole because the component lives inside it; the comparison skips every node that a page script inserted into a region, such as the marker of the table of contents or the notes column, and leaves it in place. When the nodes of the page and of the region on screen do not line up, it replaces all children of the region. Otherwise it reloads the page. A page script that keeps references to elements inside a region reads them again on `bake:content`. An element with `data-line` whose HTML is not in the old page counts as changed: it is highlighted, and when it is off screen a notice names the `##` or `###` section of its line. Double-clicking an element with `data-line` opens `vscode://file/<path of the index.md>:<line>:1`. A theme without these attributes still works in `bake dev`; its pages reload on every save.

### What a theme writes for copying

`src/copy/copy.js` is the module `bake/copy`, which the theme compiler resolves for every theme, so a theme's page script imports it like a package. `startCopy(article, { copied })` handles every copy of a selection that intersects `article`, the element that holds the article, and calls `copied()` afterwards so that the theme can confirm the copy. It throws when the page has no source script, described below. The code that writes a selection as Markdown and HTML, `src/copy/selection.js` together with `src/copy/markdown.js` and the serializer in `src/markdown/serialize.js`, is a separate module chunk, `assets/selection-[hash].js`. `startCopy` imports it on the first `selectstart` or `contextmenu` event inside `article` or on the first `keydown` event with the Meta or the Control key, so a page on which the reader copies nothing never loads it. A copy after the chunk has loaded sets the clipboard data in the copy event handler. A copy of a selection that intersects `article` before that cancels the copy of the browser and writes the clipboard with `navigator.clipboard.write` and a `ClipboardItem` whose `text/plain` and `text/html` values are promises that resolve once the chunk has loaded; Chromium and Safari accept such a write with the user activation of the copy. `copied()` is called when the write succeeds. When the write fails or the chunk cannot be loaded, the module writes the selected text with `navigator.clipboard.writeText` and does not call `copied()`. A browser without `navigator.clipboard.write` or `ClipboardItem` keeps its own copy, which puts the selected text and HTML of the page on the clipboard. `copyArticle()` writes the whole `index.md` to the clipboard and returns a promise, and `articleSource()` returns that text, or null on a page without the source script, such as the homepage. `selectionMarkdown(range, article)` imports the chunk when it has not loaded yet and returns a promise of the Markdown and the HTML that a copy of `range` puts on the clipboard, or of null when the range holds nothing to copy or the chunk cannot be loaded. A chunk that cannot be loaded is not requested again on that page, and a copy then stays the browser's own copy. Every published article page carries the whole `index.md` for this, including the front matter and HTML comments, so readers can see every HTML comment in the source. The module reads Bake's HTML described above and these parts, which the theme writes:

| Part | Meaning |
|---|---|
| `<script type="application/json" class="bk-source" data-region="source">` | The `source` of the article structure as JSON, once per page, with every `<` written as `\u003c` so that the text of the article cannot close the script element. Because it is a region, `bake dev` replaces it after every save. |
| `data-line` and `data-end-line` | The `line` and `endLine` of the part of the article structure that an element shows: a block, a heading or a sidenote. |
| `data-sidenote="1"` and `data-label="gemm"` | Together with `data-line` and `data-end-line`, the element that shows sidenote 1, with the `label` of the sidenote. A copy of it, such as one in the margin, is inside an element with `data-ui`. |
| `data-ui` | An element that is part of the theme's interface, such as a section number, a heading link, the number in front of a sidenote or a label. Copying leaves out the element and its content. |

On a copy, the module drops the part of the selection outside the article and puts two formats on the clipboard. The `text/plain` format is Markdown:

- An element with `data-line` and `data-end-line` whose text the selection covers from its first to its last character is copied as those lines of the source. An element that shows a component counts as covered when any part of it is selected, and so does a heading when the selection continues beyond it.
- Other blocks are converted from the page: paragraphs, headings, lists, quotes, code blocks, display formulas, tables, list tables, figures, asides, folds, components, embedded content and reference lists. Inside them, highlights, bold, italics, strikethrough, inline code, links, citations, equation references and formulas are written as `==…==`, `**…**`, `*…*`, `~~…~~`, backticks, `[…](…)` with the site address of an internal link, whose anchor `fragmentOf` percent-encodes, `[@key]` with the key from `data-key`, `\eqref{label}` with the label that `idOfFragment` reads from the link, and `$…$` from `data-tex`. A reference list entry is written as `- [@key]` with the key from `data-key`. Raw HTML can write an element with class `citation` or a reference list whose entries have no `data-key`; such a citation is copied as a link and such a list as an ordinary list. The module builds an mdast tree of the copy, in which the copied source lines are `verbatim` nodes, and `serializeMarkdown` from `src/markdown/serialize.js` writes it, so plain text is escaped with a backslash where Markdown or Bake would read it as syntax and the copy renders the same text. mdast-util-to-markdown escapes the CommonMark and GFM syntax, such as `[`, a backtick, `$`, `~~`, a `_` that is not between two letters or digits, a `<` that starts a tag, a `&` that starts a character reference, a `|` in a table cell, and a heading `#`, a `>`, a list marker or the `.` after a list number at the start of a line. Bake's extensions also escape each `=` of `==`, the `\` of `\eqref{` and `:::` at the start of a line, and a `*` is escaped unless it has whitespace on both sides, because only then can it not start emphasis. Chinese text and other punctuation stay as they are, and inline code, formulas and link addresses are never escaped. A list table is written with `*` before each row and `-` before each cell. A table is copied with its header row and every row that the selection touches. A heading or a component inside another block is written with the attributes from its `data-attributes`, so it has exactly the attributes written in the source.
- A selection inside one paragraph, heading, list item, table cell or fold title gives its inline Markdown without a block marker, and a selection inside one code block gives the selected code.
- A sidenote number is written as `[^label]`, with the label from `data-label`. The definition of every footnote that the copied text refers to is appended once at the end, as written in the source, unless the copied lines already contain it. A selection inside a sidenote gives its text without the `[^label]:` marker.

The `text/html` format is the selected HTML, together with the elements around the selection up to the block, reduced to plain semantic HTML: paragraphs, headings, lists, quotes, `pre` and `code`, tables, figures with images and captions, links, `strong`, `em`, `mark`, `del`, `sup`, `sub`, `cite`, `br` and `hr`. Elements with `data-ui`, sidenote elements, component boxes, embed source lines, buttons, scripts and SVG are removed, a fold title becomes a paragraph, and every other element, such as a theme wrapper, an aside or an embed, is replaced by its content. The only attributes left are `href`, `src`, `alt`, `width` and `height` of images, `start` and `value` of lists, and `align`, `colspan` and `rowspan` of table cells. Each formula is replaced by its TeX between `$` or `$$`, and every link and image address is absolute, resolved against the address of the page. Each sidenote number links to `#footnote-1` and so on, and the HTML ends with an `<hr>` and an `<ol>` that holds the text of every sidenote that the selection refers to, one `<li value="1" id="footnote-1">` each, in the order of their first reference. When the selection lies only in elements with `data-ui`, or outside the article, the browser copies it unchanged.

### The essay theme

`home.jsx` writes the homepage: the site title and description, a bar that stays at the top of the screen with the chips and the switches, and the cards. While the bar is stuck at the top, it spans the whole width of the screen with a line and a soft shadow at its lower edge, which fade in. Each switch slides a thumb to the chosen value: `home.jsx` writes the number of values of the switch on it as `--n` and the index of the chosen value on `<html>` as `--group-index` and `--columns-index`, and the script in the head and `home.js` update the index when they apply a stored or a new choice. When the blog has no published articles, the homepage has no bar and shows one line that says there are no posts yet, in a dashed frame. Below 600 pixels the chips take a full line of the bar and the switches go on the line below. Titles and summaries break long words so that they stay inside the card. A card shows the article's preview, its first image when it has no preview, or a block in the category colour with the title when it has neither, and while the pointer rests on it or it has keyboard focus, it rises by 3 pixels, a shadow fades in under it, its image grows slightly and its outline takes the category colour, or the accent colour when no categories are set. With scripts, the page scripts read this list and show the table of contents in the style that the reader chose in the settings, or else the style of the article or the site:

| Style | 1340 pixels and up | 1000 to 1339 pixels | Below 1000 pixels |
|---|---|---|---|
| `notes` | The list stays in the left column while the page scrolls. When the pointer rests on the entry or on the card at that moment, the card stays closed until the pointer leaves the table of contents and the card or moves to another entry; otherwise the card opens again as soon as the pointer reaches an entry. When keyboard focus is in the card, Escape moves it to the last entry of the chapter and the card stays closed. Below 1000 pixels the handle and the settings button sit on the left edge, and while the `buttons` setting is `autohide` both slide out of view when the reader scrolls down and return when the reader scrolls up; on an article without `##` headings, which has no handle, the settings button does this alone. While they are out of view, and while the drawer is open, they are hidden with `visibility: hidden` once the slide ends, so the keyboard does not reach them. With reduced motion they fade out and in where they are instead of sliding. The theme sets `--chat-hidden` to 1 and `--chat-visibility` to `hidden` at the same time, so the entry button of the AI chat slides out to the right with them.

The styles are in `styles/`. `tokens.css` defines every colour once as a CSS variable with the value `light-dark(light colour, dark colour)`, including the colours of the tabs, the capsules, the shadows and the drawer scrim. The value of a shadow has a `light-dark()` colour in each layer, and a layer that only one scheme has is transparent in the other. `:root` sets `color-scheme: light dark`, so the colours follow the system color scheme, and `data-theme="light"` or `data-theme="dark"` on `<html>` sets `color-scheme` to that scheme. The default build target of Vite, Chrome 111, Firefox 114 and Safari 16.4, predates `light-dark()`, so lightningcss rewrites each `light-dark()` in the compiled stylesheets as a choice between two variables that `:root` sets for the current scheme. The variables of the published stylesheets therefore hold the values of the current scheme, which a page script or a component reads with `getPropertyValue`. It also holds the stacking order of the parts that overlap the page as one list of `--layer-…` variables, ordered from the bottom to the top: the sticky bar of the homepage and the left column of the table of contents, the tabs, dots and ticks, the phone handle, the preview card, the chapter cards and the notes panel, the settings, the drawer scrim, the drawer, the chat entry button, the button that asks about the selected passage, the chat panel and the toast. Every `z-index` in the essay styles that places an element among these parts uses one of these variables, and so do the entry button, the ask button and the panel of the chat. The other `z-index` values order the parts inside one element that is its own stacking context, such as the draft label, the shadow and the border of a homepage card, and stay numbers. `page.css` defines the column widths as variables for each breakpoint: 1340 pixels and up, 1000 to 1339 pixels, and below 1000 pixels. Each setting has its values, its initial value and the pages it applies to: `theme` and `font` apply to article pages, the homepage and the 404 page, `toc` and `buttons` only to article pages. The initial value of `toc` is the style of the article. `settingAttributes(page, article)` returns the initial values of the settings of a page as `data-<name>` attributes, which `page.jsx`, `home.jsx` and `not-found.jsx` write on `<html>`. The choice is stored in `localStorage` as `bk-<name>`, and an inline script in the head replaces each `data-<name>` that the page has with the stored choice before the first paint, so a stored choice overrides the style of the article. On the homepage the same script also applies the stored grouping and column count, `bk-group` and `bk-columns`, over the defaults that the page writes from `bake.config.js`. The homepage hides its switches and tag chips, and an article page hides the `copyMarkdown` button, unless `data-script` is set. The same script sets `data-script` on `<html>`; the styles hide the sidenotes under their blocks only when it is set, so a reader without scripts sees every sidenote under the block that refers to it. `prepaintScript(pageSteps)` in `settings.js` writes this script, and `homePrepaintSteps(groups)` gives the steps of the homepage. The script does all of this only when the page is served over `http:` or `https:`. A page opened from a `file://` address has no `data-script` and does not apply the stored choices, because the browser loads none of its module scripts there, as described in "Themes"; it is the page without scripts, with its stylesheets and images, every sidenote under its block, `componentNeedsScript` in every component frame and no switches, tag chips or `copyMarkdown` button. The 404 page links its files from the site root, so opened from a file it finds no stylesheet. Page scripts that change the layout dispatch the `bk:layout` event on `document`, and the scripts that measure the layout listen to it. `widths.js` and `notes.js` read the blocks and sidenotes again on `bake:content`, `toc.js` reads the list and the headings again and rebuilds the view of the current style, keeping the phone drawer open, `preview-card.jsx` looks up the template of a link each time it shows a card and hides the card on `bake:content`, and the other scripts listen on `.bk-article` or `document` instead of on single elements, so they work on replaced content without changes. `settings.jsx` dispatches `bake:theme` on `document` when the reader chooses another theme and, while the theme setting is `system`, when the system color scheme changes.

A code block, a table or a display formula wider than its column scrolls horizontally inside its own box. A soft shadow at each edge behind which content is hidden marks that it scrolls: `blocks.css` draws the shadows and the covers that hide them at the ends as backgrounds of the scrolling element, with the covers attached to the content, so the shadows follow the scroll position without a script, and a table keeps the border and the rounded corners of its frame. The covers take the colour of the box behind the content from `--scroll-cover` and the shadows take `--scroll-shadow` from `tokens.css`. A list table cell that holds text is at least 9em wide, so on a narrow screen the table scrolls instead of breaking its text into a column of single characters; a cell that holds only an image or a formula keeps its natural width.

An example shows its source and its result side by side when its block is at least 880 pixels wide, and gives its block the natural width 880 pixels, so `widths.js` places it in the wide column when the screen has one. An example with `data-result-widths` always shows its source above its result, so the result has the full width of the block: its block takes the `naturalWidth` and `width` that Bake gives it, and the body width otherwise. A component or figure with a pixel width inside it keeps that width when the column allows it, and a component without a set width spans the result. The source has a lighter shade of the code background, a line separates it from the result, and both have the same padding. The first and last lines of text in each part are trimmed to the cap height and the baseline with `text-box`, so the first line of the source and the first line of the result start at the same height. A display formula in the result is set at the size of the text, so the aligned formulas of the syntax article fit beside their source; a wider formula scrolls inside the result.

The component frame is styled in `blocks.css` like a figure: border, radius and background from the tokens, none of them with `data-frame="none"`, and the caption styled like a figure caption. The placeholder box keeps the declared height at every screen width, `--component-narrow-height` and `--component-narrow-ratio` below 600 pixels, and shows a striped background until `data-state` is `ready`. The custom element inside the box has `display: block` and `height: 100%`, so the frame keeps its height when the component loads. Buttons, labels, inputs and other controls that are not disabled show the pointer cursor, inside a component as on the rest of the page; one rule in `page.css` sets it. When `<html>` has no `data-script`, every box shows the text `componentNeedsScript` from `labels.js` in its centre, and a box whose frame has `data-state="failed"` shows `componentFailed`. `page.jsx` passes both texts to the styles as the CSS variables `--bk-component-needs-script` and `--bk-component-failed` on `<body>`, so the HTML that Bake writes for a component stays the same in every theme.

Components own their content, so the essay styles do not reach into the component box. Every rule that styles the article, and the page-wide rules for links, buttons and focus outlines, ends its selector with `:where(:not(.component-box *))`. `:where()` adds no specificity, so the rules keep their order of precedence. The only styles that apply inside the box are inherited properties such as the font and the text colour, the page-wide `box-sizing: border-box`, the selection colour, the pointer cursor on controls that are not disabled, and `display: block` and `height: 100%` on the custom element itself. A new rule in the essay styles whose subject can be an element inside a component needs the same ending.

### The bento theme

The bento theme lays out the same article structure as a grid of cards. It keeps the look of the essay theme by importing its files with relative paths such as `../essay/styles/tokens.css`: `client.jsx` imports the essay stylesheets for fonts, colours, text, blocks, settings, the homepage, the 404 page and printing, and starts the essay scripts `widths.js`, `folds.js`, `toast.jsx`, `heading-links.jsx`, `copy.js`, `preview-card.jsx`, `settings.jsx`, `home.js` and `not-found.js`; `page.jsx` uses the essay `header.jsx`, `meta.jsx`, `previews.jsx`, `labels.js` and `settings.js` and writes the source script of the essay page; `article.jsx` uses `arrange`, `subsectionOf`, `Block`, `HeadingLink` and `Sidenotes` from the essay `article.jsx`, and calls `arrange` with `recaps: true` so that the sidenotes of the recaps it shows belong to their card; `home.jsx` and `not-found.jsx` re-export the essay homepage and 404 page; and `theme.css` imports the essay `theme.css`. bento therefore writes the same document head, the same `copyMarkdown` button and the same `data-line`, `data-end-line`, `data-label` and `data-ui` attributes as essay, so copying works as described in "What a theme writes for copying", and it can be the site theme. These imports leave the theme folder, so they always load the built-in essay files, and a blog's `themes/essay/` does not change bento. `styles/bento.css` holds the grid, the cards and the sidenotes and sets the essay width variables `--body-width`, `--wide-width` and `--page-width` to the full width of the element that holds the block, so every width level fills its card. `page.jsx` loads every entry of `assets.scripts` as a module script, which includes the AI chat, and the essay `settings.css` sets `--chat-bottom` to the bottom offset of the settings button, so the chat button at the bottom right and the settings button at the bottom left sit on one line at every width. From 1000 pixels up, the page keeps a gutter of 124 pixels on both sides: the chat button, about 86 pixels wide with the Chinese or the English label and 16 pixels from the right edge, ends about 102 pixels from that edge, so the gutter leaves a gap of about 22 pixels between it and the cards, and the settings button, which ends 50 pixels from the left edge, gets the same gutter so that the grid stays centred; neither button covers a card or the text before the first section; the grid is at most 1340 pixels wide and centred. Below 1000 pixels the button covers the edge of the page as it does in the essay theme. The widths of the cards are fractions of a pixel, so `bento.css` draws the scroll shadows of a code block, a table or a display formula 1 pixel inside the edges of its box and 2 pixels shorter than the box, and the covers taller than the box, so a box whose content fits shows no line of shadow at its edges. Its rules leave the content of a component alone in the same way as the essay styles: a rule whose subject can be an element inside `.component-box` ends its selector with `:where(:not(.component-box *))`.

`article.jsx` writes the blocks before the first `##` heading and their sidenotes into `<div class="bt-intro">` under the masthead, and each `##` section into `<section class="bt-card">` inside `<div class="bt-grid">`: the heading with its number, the section's `recap` as `<div class="recap bt-recap">` under the heading, set as a subtitle in the recap colour without the bar that marks the recap of a subsection, which `bake/copy` copies as a `:::recap` block, the blocks with the `recap` of each `###` subsection under its heading, and `<div class="bt-notes">` with the sidenotes that the section refers to, in its title, its blocks or its recaps, in the order of their first reference, right after the last block. ## Vite builds

`src/bundle/vite.js` holds the Vite configuration that every build of Bake shares: the root is the Bake folder, Vite reads no configuration file and no `.env` file and logs nothing, and every module uses one copy of `solid-js`. `browserBuild({ input, plugins, alias, stylesheet })` builds ES modules for the browser in memory, inlines no asset and returns the file name of the entry chunk, the stylesheets that the entry chunk and the chunks it imports statically load, the output files as `{ path, source }` and the modules that went into them. The build splits the code into chunks: a module that is loaded with a dynamic `import()` gets its own chunk, a module that several chunks share goes into a shared chunk, and MathJax goes into a chunk named `mathjax-[hash].js`. Each chunk gets the stylesheet of the CSS it imports, and the code that Vite writes for a dynamic `import()` loads the stylesheets of the target chunk before the import resolves. Every output file is named `assets/[name]-[hash]` with its extension, except the stylesheets when `stylesheet` names them. Rolldown replaces characters such as `#` and `%` in these names with `_`, so a theme named `plain#1 %` writes `assets/plain_1 _-[hash].js`. The page script of a theme, the components and the AI chat are one build each, and so is the `theme.css` of the site theme, which gives only a stylesheet and names it `_bake/theme.css`.

`src/bundle/modules.js` lists the public modules of Bake in one table, together with the builds that resolve each of them: `bake/copy` and `bake/fragments` for themes, `bake/math` for components and the AI chat, and `bake/kit` for components. `publicModules(importer)` returns them as Vite aliases for the themes, the components or the AI chat. `bake/math` imports two virtual modules, `bake:preamble` with the macro definitions of the blog and `bake:math-font` with a loader for each font file of MathJax, which `mathModules(preamble)` provides; a theme cannot import `bake/math` or `bake/kit`, because a theme is compiled without the preamble. When Bake reads components in Node, `bake/math` resolves to `src/components/node-math.js`, whose `texToSvg` throws.

## Components

A component is an interactive block that a blog writes. `components/` in the blog holds one component per file, `name.js` or `name.jsx`. The file name is both the custom element name and the block name in Markdown, so it uses lowercase letters and digits with at least one `-`, and it cannot be the name of a built-in block such as `list-table` or one of the names that the HTML standard reserves and does not allow as custom element names: `annotation-xml`, `color-profile`, `font-face`, `font-face-src`, `font-face-uri`, `font-face-format`, `font-face-name` and `missing-glyph`. `components/lib/` holds code and CSS that components share; files there are not components. A component may import `components/lib/`, npm packages from the blog's `package.json`, `solid-js`, which resolves to Bake's own copy, `bake/math` and `bake/kit`.

A component module exports three things:

| Export | Contents |
|---|---|
| `params` | The parameters, as `{ name: { label, type, default, … } }`. `label` is the text shown next to the parameter's control, `default` is required and must be a valid value. The types are `number` with optional `min`, `max` and `step`, `text`, `boolean`, `enum` with `options`, a list of strings, and `file`, a path relative to the article folder that must name a file there, such as `grid.json`. `width`, `height`, `id` and `class` are reserved for Bake. A component without parameters may leave `params` out. |
| `layout` | `width`, the width that `auto` resolves to: `body` (the default), `wide`, `page`, a size in pixels such as `560px` or a percentage of the body column up to `100%`. `height`, required, the height of the placeholder: a number of pixels, `{ ratio: 16 / 9 }` (width divided by height) or a function of the converted parameters that returns either. `narrowHeight`, in the same forms, used below 600 pixels of screen width instead of `height`. `frame: false` drops the border and background and keeps the width and the caption. |
| default | A SolidJS function component, which Bake wraps into a custom element and renders with the parameters as reactive props, or a class that extends `HTMLElement`, which reads `this.params`. Bake sets `params` before the element is connected and calls `update()` when they change. |

An article writes a component as a block, `:::act-fn-plot{fn=gelu range=6 width=560px height=420}`, with the caption between the fences; the caption may be empty. The attributes are converted to the declared types: a bare attribute such as `{toggle}` is `true`, a number must be a number within `min` and `max`, a boolean `true` or `false`, an enum one of its options. An unknown attribute, a value of the wrong type or out of range, and a file that is not in the article folder are reported at the attribute's column. Parameters the article does not set get their defaults, so the component always receives every parameter. `width` takes `body`, `wide`, `page`, `auto`, pixels or a percentage up to `100%`; `auto` or no width uses `layout.width`. `body`, `wide` or `page` gives the block that `width`. A percentage gives the block the width `body` and the frame that share of the body column. A pixel width gives the block `naturalWidth`, so the theme places it like a figure with a pixel width, and the frame that width; the frame is centred and never wider than its column or the screen. `height=420` is a number of pixels that replaces both `layout.height` and `layout.narrowHeight`. `:::{width=…}` around a component, `float` on a component and an `#id` or `.class` on a component are errors. A `file` parameter, such as `points=glu-points.json`, keeps the path as written in `params` of the article structure, and the component receives it URL-encoded in `data-params`, such as `data%231.json` for `data#1.json`. The build publishes the file with the article, so the component can fetch the value relative to the page. `layout.height` functions run at build time with the converted parameters. Components inside other blocks, such as `:::example` and `:::fold`, are checked and rendered the same way.

Bake reads `params` and `layout` in Node with Vite before it parses the articles, so a component module must not use a browser API such as `window`, `document`, `navigator`, `location`, `localStorage`, `customElements`, `matchMedia`, `getComputedStyle`, `requestAnimationFrame`, `ResizeObserver` or `IntersectionObserver` at the top level, also not in the files it imports from `components/lib/`. Such a use is reported at its position, for example `components/lib/size.js:3:23 lib-plot: components/lib-plot.js uses the browser API window at the top level; the build reads params and layout in Node, so use it inside the component code`. `class … extends HTMLElement` at the top level works, because `HTMLElement` is defined while the module is read. Problems in `params` and `layout` and a missing default export are reported at the start of the component file, prefixed with the component name.

`src/components/bundle.js` builds the components that published articles use in one build of `browserBuild`, described in "Vite builds": the runtime `src/components/runtime.js` as the entry and one chunk per component that the runtime imports when it needs it, with shared chunks for `components/lib/`, `solid-js` and MathJax, whose chunk is named `mathjax-[hash].js`, and one stylesheet per chunk that loads with it. The build marks the JavaScript modules of `bake/kit` as free of side effects, so a component gets only the kit modules whose exports it uses, with their stylesheets, and a kit module that several components use goes into a shared chunk in the same way as a file of `components/lib/`. The files are written to `dist/assets/` under names that contain a content hash. A page with components loads the runtime as a module script; a page without components loads no component code. The runtime finds the frames on the page, and again on `bake:content` after `bake dev` replaced the article, and starts a component when its frame comes within 800 pixels of the viewport, and every component before printing: it loads the component's chunk, defines the custom element once, creates the element, sets `params`, appends it to the box and sets `data-state="ready"` on the frame. When the chunk cannot be loaded, or the constructor, the `params` setter or `connectedCallback` throws while the runtime creates and appends the element, the runtime removes the element, sets `data-state="failed"` and logs the error to the console. The browser reports an exception from a custom element callback as an `error` event on `window` and `append` returns normally, so the runtime listens for that event while it appends. Without scripts the page shows the frame, the placeholder and the caption.

Themes dispatch `bake:theme` on `document` when the colors of the page change. A component that draws with canvas or WebGL redraws on it.

`bake/math` exports `texToSvg(tex, { display = false } = {})`, which returns a promise of an `<svg>` element. It typesets the formula with MathJax 4 in the browser, with the TeX packages and the New Computer Modern font that `src/render/math.js` uses and with the macros of the blog's `preamble.sty`. The font keeps less common glyphs, such as double-struck letters, in separate files that MathJax loads when a formula needs them, which is why the function is asynchronous. A TeX error rejects the promise. MathJax is part of the component bundle only when a component imports `bake/math` or `bake/kit`. A page downloads it only when one of its components imports `bake/math` or shows a TeX label of the kit, because the kit loads `bake/math` with a dynamic import the first time it typesets a label.

A component's own CSS, including CSS in `components/lib/`, uses class names that start with the component's prefix, such as `act-` for `act-fn-plot`, so that components on the same page and the theme do not style each other.

### The kit

`bake/kit` is an optional library for writing SolidJS components, in `src/kit/`. A component that does not import it gets none of its code, and a component that imports it shares one copy of the kit and of Solid with every other component on the page. The kit's modules use no browser API at the top level, so the build can read the `params` and `layout` of a component that imports it. Each part that renders imports its own stylesheet, `controls.css`, `plot.css`, `legend.css` or `tex.css`, so a component that imports only the plain helpers loads none of the kit's styles. `src/kit/index.js` exports these parts:

| Export | What it is |
|---|---|
| `Controls` | A row that wraps its children, the controls of a component. |
| `Slider` | A labelled range input: `label`, `min`, `max`, `step` (1 when not set), `value`, `onInput(number)` and `format(number)`, which writes the value next to the slider and shows the decimals of `step` when not set. The accessible name of the slider is its label, and the formatted value is its `aria-valuetext`. The part of the track left of the thumb has the accent colour. |
| `Segmented` | One choice out of a few: `label` for assistive technology, `options` as strings or `{ value, label }`, `value` and `onChange(value)`. It is a group of radio inputs, so the arrow keys move the choice. Each segment is 24 pixels tall, and the background and the frame of the chosen segment are a layer that fades in. |
| `Toggle` | A switch: `label`, `checked` and `onChange(checked)`. It is a checkbox with the role `switch`. |
| `Button` | A button: `onClick()`, `disabled` and its children as the text. |
| `Plot` | An SVG plot: `x` and `y` as `[start, end]`, `width` and `height` in pixels, `margin` with any of `left`, `right`, `top` and `bottom` (34, 8, 8 and 22 by default) and `label` for assistive technology. Without `width` and `height` it fills its parent and follows its size. It tracks the pointer and gives its children the scales through `usePlot()`. `pointer` and `onPointer(x)` share the x value under the pointer between plots: every plot shows the crosshair at that value, and the plot under the pointer shows the readout. |
| `Axes` | Inside a `Plot`: grid lines, tick labels from `niceTicks` and the two axes through zero when zero is in view. `grid={false}` leaves out the grid. |
| `Curve` | Inside a `Plot`: the graph of `f`, sampled every 2 pixels and at least 40 times across the plot, or `samples` times when that prop is set, with `color`, `dashed`, `breaks` (x values where the line is not joined) and `label`, the name in the readout. Values that are not finite leave a gap. |
| `Crosshair` | Inside a `Plot`: a vertical line at the pointer, a dot on every curve and a readout box with x and the value of every curve that has a `label`. `xLabel`, `xDigits` (2) and `yDigits` (3) set the readout. The line, the dots and the values are placed at the x value rounded to `xDigits`, the value the readout shows. The box is placed beside the pointer inside the plot. |
| `Legend` | A row of items `{ label, tex, texWidth, color, dashed }`: a swatch in the curve style and the TeX label, or the text label when the item has no `tex`. |
| `Swatch` | The line sample of the legend and the readout: `color` and `dashed`. |
| `Tex` | A TeX formula in HTML: `tex`, `width`, the minimum width the formula takes before it is typeset, so that the text around it does not move when it arrives, and `label`, its accessible name, which is the TeX source when not set. It has the role `img`. |
| `SvgTex` | A TeX formula inside an SVG: `tex`, `x`, `y`, `anchor` (`start`, `middle` or `end`) and `baseline` (`top`, `middle` or `bottom`). It measures the typeset formula and places that point of its box at `x` and `y`, and it stays hidden until then. Like `Tex`, it has the role `img` and the accessible name `label` or the TeX source. |
| `niceTicks(low, high, count)` | About `count` ticks between `low` and `high` with a step of 1, 2 or 5 times a power of ten, as `{ value, label }`. |
| `formatNumber(value, digits)`, `stepDigits(step)` | A number with a fixed number of decimals and a minus sign (U+2212), and the number of decimals that a step is written with, such as 2 for 0.25 and 1 for 2.5. |
| `linearScale(domain, range)` | A function from the domain to the range, with `invert` for the way back. |
| `samplePath(f, domain, x, y, samples, breaks)` | The SVG path of `f` that `Curve` draws, for components without Solid. |
| `createTween(target, { duration })` | A signal that follows the accessor `target`, a number or a list of numbers, over `duration` milliseconds (200 by default) with an ease-out curve. With `prefers-reduced-motion: reduce` it takes the new value at once. |
| `prefersReducedMotion()` | Whether the reader prefers reduced motion. |
| `createElementSize(element)` | A signal with the `width` and `height` of the element that the accessor returns, measured with a `ResizeObserver` from the moment the component mounts. |

The TeX labels of `Tex`, `SvgTex` and `Legend` are typeset by `texToSvg` from `bake/math`, so they use the macros of the blog's `preamble.sty`, the same as the article body. A label that cannot be typeset shows its TeX source, and the kit logs an error to the console that starts with the name of the component, such as `act-fn-plot: the TeX label "\frac{" cannot be typeset: …`; the rest of the component keeps working. The kit's CSS classes start with `bk-kit-`. Its colours, fonts and easing come from the theme's CSS variables: `--ink`, `--ink-2` and `--ink-3` for text, `--line-2`, `--grid` and `--axis` for lines, `--surface` and `--surface-2` for backgrounds, `--accent` for the active state of controls, `--shadow` for the readout, `--font-mono` for numbers and `--ease-out` for the timing function of its transitions. Series colours are passed as props, such as `color="var(--series-1)"`. The parts therefore follow dark mode and the theme setting without a redraw. Every control shows the pointer cursor and an outline in the accent colour when it has keyboard focus. A change of state, such as a toggle switching, a segment being chosen or the readout appearing, is a CSS transition of at most 150 milliseconds; nothing moves when the reader does not act. With `prefers-reduced-motion: reduce` the kit runs no transition and no tween.

## AI chat

Readers chat with DeepSeek about the article they read or about the whole blog, with their own API key and without a server. `src/chat/entry.js` is the chat module that every article page and the homepage load. It is independent of the theme in the same way as `bake/copy`: it reads the parts of the page that every theme writes and draws its interface itself.

The chat does not depend on the blog, so `src/chat/bundle.js` builds it with Vite once and every build of every blog copies the same files to `dist/assets/`. Its formulas use the macros of the blog through `_bake/preamble.json`, which the chat module fetches when it first loads `bake/math`. The build is kept in `bake-chat/` in the temporary directory of the system. An index file named after the location of Bake holds the installed versions of the packages that compile, bundle and minify the chat, which are `vite`, `rolldown`, `lightningcss`, `vite-plugin-solid`, `@babel/core`, `babel-preset-solid`, `babel-plugin-jsx-dom-expressions` and `solid-js`, the content hash of every module that went into the bundle and of every file in `src/chat/` and `src/bundle/`, and the folder that holds the output. A build copies the cached files when the versions are the same, the index lists every file of those two folders and every hash matches. Otherwise it builds the chat, writes the output to a temporary folder and renames that folder to a name made of the location of Bake and the hash of the output, writes the index to a temporary file and renames it over the old index, and removes every other output folder of the same location. Two builds that miss the cache at the same time write folders of the same name, so they leave one output folder. A process keeps the bundle in memory, so `bake dev` builds or reads it once. The chat has its own copies of `solid-js` and MathJax, so a page with components and math loads them twice when the reader opens the chat and an answer has a formula.

The module first checks that the page can use a passkey with the PRF extension of WebAuthn: the page is a secure context, its host name is not an IP address, which WebAuthn does not accept as a relying party, `PublicKeyCredential` exists and `PublicKeyCredential.getClientCapabilities()` reports `extension:prf` as true. When the browser has no `getClientCapabilities()`, or the call fails, the module shows nothing either. So the chat appears on sites served over HTTPS and on `localhost`, including `bake dev`, and not at `http://127.0.0.1`. Without scripts the page shows nothing of the chat.

The module appends `<div data-bake-chat>` to the body and draws everything in its open shadow root, so the styles of the theme do not reach the chat and the chat styles do not reach the page. It holds the entry button in the bottom right corner, the button that asks about the selected passage, and the panel. The panel is a separate chunk that the module imports on the first click. Inherited CSS variables pass into the shadow root, so the chat uses these variables of the theme: `--bg`, `--surface`, `--surface-2`, `--ink`, `--ink-2`, `--ink-3`, `--line`, `--line-2`, `--accent`, `--card-shadow`, `--font-ui`, `--font-body`, `--font-heading`, `--font-mono` and `--ease-out`. The host of the shadow root sets `all: initial` and then `color-scheme: inherit`, so the chat uses the color scheme of the page for `light-dark()` colours and for the parts that the browser draws, such as scroll bars. A theme sets `--chat-right` and `--chat-bottom` to move the entry button, 16 pixels each by default, and `--layer-chat-button`, `--layer-chat-ask` and `--layer-chat-panel` to place the entry button, the button that asks about the selected passage and the panel in its stacking order, 75, 76 and 77 by default; the essay theme sets `--chat-bottom` to the bottom offset of its settings button, so both buttons sit on one line. A theme hides the entry button by setting `--chat-hidden` to 1, which slides it out to the right and fades it, and `--chat-visibility` to `hidden`, which takes it out of the keyboard order once the slide ends; `0` and `visible`, the defaults, bring it back. With reduced motion it only fades. Switching between the views of the panel (entering a key, unlocking it and the conversation) fades and slides the new view in, and the folded reasoning of an answer opens and closes with a transition of its height; with reduced motion both only fade. UI text comes from `src/chat/labels.js`, in Chinese when the `lang` of the page starts with `zh` and in English otherwise.

The figure on the entry button and in the panel header is a separate part, `src/chat/figure.js`. `createFigure()` returns `{ element, setState(state) }`, and the states are `idle`, `greet` (the pointer rests on the entry button), `waiting` (a request is sent), `answering` (text arrives) and `failed`. Another figure replaces this file with the same interface. The figure moves only when its state changes.

The chat reads these parts of the page:

| Part | Use |
|---|---|
| `<script class="bk-source">` | The Markdown source of the article, read with `articleSource()` from `bake/copy`. A page without it is not an article page, and its chat is about the whole blog. |
| `data-region="article"` | The element that holds the article. Its `h2` and `h3` elements with an `id` give the outline that the model uses to link sections, without the elements with `data-ui`. A selection inside it shows the button that asks about the passage, and `selectionMarkdown()` from `bake/copy`, which the chat waits for, turns the selection into the quoted Markdown; when it gives null, the panel opens without a quote. |
| `og:site_name` and `og:title` | The names of the site and of the article in the instructions to the model, with the host name and the document title when the tags are missing. |

The API key is stored only in encrypted form, by `src/chat/vault.js`. When the reader saves a key, the module first checks it with `GET /models`. It then creates a passkey for the host name of the page with user verification and evaluates the PRF extension with a random 32 byte salt, during the creation when the authenticator supports that and with a second request otherwise. HKDF with SHA-256 turns the PRF output into a non-extractable AES-GCM key of 256 bits, which encrypts the API key with a random 12 byte IV. `localStorage` holds `bk-chat-key` with the credential id, the salt, the IV and the ciphertext, each in base64url, and nothing else. Opening the panel asks for the passkey once on every page load and keeps the decrypted key in the memory of that page, so a reload or another page asks again. Clearing the key removes `bk-chat-key` and reports the credential as unknown with `PublicKeyCredential.signalUnknownCredential()`, so the browser can offer to delete the passkey. Saving another key reports the credential of the old key in the same way, and so does a passkey that was created but gives no PRF output, after which the panel says why and nothing is stored. There is no way to store the key unencrypted.

The browser sends the requests directly to `https://api.deepseek.com/chat/completions` with the model `deepseek-flash`, streaming the answer as Server-Sent Events. The reader turns DeepSeek's thinking mode on and off, and the choice is stored as `bk-chat-thinking`; the reasoning of the model is shown folded above the answer and sent back with the following requests as DeepSeek requires. In the chat about one article, the instructions hold the whole `index.md` and the outline. In the chat about the whole blog, the module fetches `_bake/articles.json` when the reader sends the first question, and the instructions hold one line per article with its address, title, date, summary, tags, category and sections. The model reads articles with the tool `read_article`, which fetches the `index.md` of a Markdown article or the text of a plain HTML page; after six rounds of tool calls the request no longer offers the tool. `_bake/articles.json` has `title`, `description` and `language` from `bake.config.js` and `articles`, the published articles and plain HTML pages that are not drafts in the order of the homepage, each with `url`, `title`, `date`, `summary`, `tags`, `category` (the name), `source` (the address of its `index.md`, only for Markdown articles) and `sections`, which lists `id`, `number`, `title` and `subsections` with `id` and `title`.

Answers are Markdown, rendered by `src/chat/reply.js` with remark, the plugin list `REMARK_PLUGINS` that articles are also parsed with, and `mdast-util-to-hast`. Raw HTML is dropped, images become their alternative text, links with a scheme other than `http`, `https` or `mailto` become plain text, links to the blog resolve against the site root, and other links open in a new tab. `\(…\)` and `\[…\]` outside code become `$…$` and `$$…$$`. Formulas are typeset with `texToSvg` from `bake/math`, so they use the macros of `preamble.sty`, and the module typesets each formula once while the answer streams. Errors of DeepSeek are shown in the panel with a retry button: a rejected key, no balance, too many requests, a conversation longer than the context length of the model, which suggests a new chat, a server error and a network error each have their own text. Only the last reply of the conversation has the retry button, and only while no answer streams; it asks the question of that reply again and replaces the reply. The stop button ends the stream, keeps the text written so far and sends it with the next question. In `bake dev`, the module reads the article source again on `bake:content`, so the next question uses the saved text.

## bake dev

`src/build/site.js` holds the steps that `bake build` and `bake dev` share. `createSite(root, { drafts, base, shareImages })` creates the state of one blog, where `drafts` set to true gives drafts a page and a card on the homepage, `base` replaces the path of `url` in `bake.config.js` as the root of the 404 page's assets and `shareImages` set to true plans the share images, and `updateSite(site, changedPaths)` reads it and renders every page: with `null` it reads everything, with a list of changed paths relative to the blog root it reads `bake.config.js`, `preamble.sty` and the components again only when one of them or a file in `themes/` or `components/` changed, parses again every article after that and otherwise only the articles whose folder contains a changed path, compiles a theme again only when a file in `themes/` changed or when the theme becomes or stops being the site theme, because only the site theme is compiled with `home.jsx`, `not-found.jsx` and `theme.css`, and bundles the components again when they were read again or when the set of components that published articles use changed. After reading, it links every article again, parsed again or not, because link errors, preview cards and embedded sections depend on other articles; linking and building the article structure take much less time than parsing.

The site state keeps the last good version of every published article: its parsed article, its entry and the outputs of its page, from the last update in which the article had no errors and every error of the update belonged to an article. An update with an error in a file that is not an article, such as a theme file or a component, leaves the last good versions unchanged, because `bake dev` does not apply that update. `updateSite` shows every article without errors as it is now and every article with errors as its last good version, and leaves out an article with errors that has no last good version. The pages it returns, the homepage, the 404 page, the feed, the sitemap and the catalog of the AI chat all come from the shown versions. The links of the other articles are checked against the last good version of an article with errors as well, so a link to the old address of an article whose slug changed together with an error, or to a heading that such an article renamed, reports no error until the article is fixed; an article with errors that has no last good version takes part in the check as it is now. For this check, an article has errors when reading its front matter or its body, or checking its address, reports an error. Bake checks the links of every article with each such article at its last good version. When an article that changed since its last good version gets link errors in that check, it counts as having errors too, and Bake checks the links of every article again with that article at its last good version as well, until no further article gets link errors. An article never stops counting as having errors during this, and only changed articles can join, so it ends after at most one check more than there are changed articles. Each article with errors checks its own links in its current version. A build starts without last good versions, so it checks every article as it is now, and a build with errors writes nothing. It returns the sorted errors, `articleErrorsOnly`, which is true when every error belongs to an article, the articles, the pages of the shown versions with their outputs, the homepage output, the outputs of the 404 page, the feed and the sitemap, the asset files of the themes and the components, the planned share images and the files of `public/`. `bake build` calls it once with `null`, copies or draws the share images with `shareImageOutputs` and writes the outputs with `writeDist`; `bake dev` keeps the state and calls it after every save.

`src/dev/watch.js` watches the blog root with `fs.watch` and `recursive: true`, ignores `dist/`, `node_modules/` and every file or folder whose name starts with a dot, and collects the paths of one save for 40 milliseconds. A path that does not exist and was not a known file before, such as a temporary file an editor writes and deletes during a save, is ignored. When the blog root can no longer be watched, because it was removed or the system has no file watches left, `bake dev` closes the server, prints `bake dev: cannot watch <root>: <reason>` and exits with status 1. `watchBlog` also watches the parent folder of the root for the name of the root, because `bake dev` runs with the root as its working directory, and the system reports no event inside a removed folder that is still the working directory of a process. `bake dev` does not reload the modules that `bake.config.js` imports; restart it after changing them.

`src/dev/preview.js` keeps the pages, the homepage, the 404 page, the feed and the sitemap that `bake dev` serves, in memory. It creates the site with `base` set to `/`, because `bake dev` serves the blog at the root of its address. When `articleErrorsOnly` is false, because the errors include a file that is not an article, such as `bake.config.js` or a theme file, it keeps everything it serves. Otherwise it serves the pages, the homepage and the site files that `updateSite` returns, so an article with errors stays at the address of its last good version. It compares the old and new pages: a page whose front matter changed, or that appeared or disappeared, is reloaded; a page whose HTML or source version changed is updated in place, so an open page always knows the version of the file it shows; the homepage is reloaded when its HTML changed, which happens when the front matter of an article changes or an article appears or disappears; and a changed path that is not an article's `index.md` reloads every page.

`src/dev/server.js` serves the pages, the homepage at `/`, `/404.html`, `/feed.xml`, `/sitemap.xml` and `/_bake/theme.css` with Node's `http` module on port 4321 or the next free port. It listens on the loopback address `127.0.0.1` unless `--host <address>` names another address, and it prints the addresses of the computer on the local network only when that address is `0.0.0.0` or `::`, which listen on every network interface. To refuse pages of other sites that a DNS name pointed at the server, it answers every request with 403 unless the host name in its `Host` header is `localhost`, ends with `.localhost`, is an IP address or equals the `--host` address, ignoring letter case. HTML pages are sent with `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: frame-ancestors 'self'`, so another site cannot show them in a frame. It adds `<script src="/__bake/client.js" data-bake-dev>` at the end of the body of every HTML page; on an article page the script carries the path of the `index.md` for VS Code, its path in the blog, the outline of `##` and `###` headings with their lines, the version of the source, which is the SHA-256 hash of the `index.md` text that the page was built from, the `params` declarations of the components the page uses, and in `data-token` a random token that the server creates once each time `bake dev` starts. `/__bake/events` is a Server-Sent Events stream with three events: `hello` with an id that changes when `bake dev` restarts, `problems` with the current problems, and `update` with the addresses to reload (`reload`, a list or `"all"`) and the addresses to update in place (`refresh`). Any address without a page answers 404 with the list of every article. `src/dev/client.js` is the page script: it keeps the HTML the page was loaded from, applies updates as described in "What a theme writes for bake dev", stores the scroll position in `sessionStorage` before a reload and restores it after, and shows the problems list and the notice in a shadow root styled by `src/dev/client.css`. The problems list opens when problems appear and closes when they are fixed. Its header shows the number of problems, a button that copies every problem line and a close button; the problems are grouped under the path of their file, and each problem shows its line and column next to its message and copies `file:line:col` when clicked. While the list is closed, a dot takes its place: it is small and grey when there are no problems and red with the number of problems otherwise, and clicking it opens the list. The list and the dot sit 46 pixels above the bottom offset `--chat-bottom` and at the right offset `--chat-right`, so they stay above the entry button of the AI chat, and below 1000 pixels the list rises another 48 pixels so that it stays above the table of contents handle and the settings button of the essay theme. A changed block is highlighted by a separate element over it in the shadow root, which fades in and out, so the page's own elements are never animated. The list, the dot and the notice fade and slide in and out with CSS transitions of opacity, translate and scale; when the reader prefers reduced motion, they only fade.


`src/dev/param-bar.js` and `src/dev/param-bar.css` add a parameter bar to every component frame with `data-line` inside a region whose component declares parameters, so embedded content gets no bar. `src/dev/client.js` loads the script on article pages. Each bar is a `<bake-param-bar data-bake-dev>` element with a shadow root that adopts two stylesheets, `param-bar.css` and `switch.css`, loaded once before the first bar is drawn, inserted in the figure before `.component-box`, so it takes the width of the frame and leaves the height of the box unchanged. The first row of the bar holds the component name on the left and the buttons on the right. Below it, a grid holds one field per parameter, with the `label` of the declaration above its control: a slider and a number field for a number with `min` and `max`, a number field for a number without both, a select for an enum, a switch for a boolean and a text field for text and file parameters. The grid has as many columns of at least 200 pixels as the bar has room for, so the fields line up in rows and a phone shows one field per row. Slider values are rounded to the decimals of `step`. Changing a control sets `params` on the running element and calls its `update()`; when the component has not started yet, the bar applies the values when the frame gets `data-state="ready"`. A field whose value differs from the value in the Markdown shows an orange dot after its label, and nothing else changes.

An update in place keeps a component frame of the article, with its running element and its bar, when the frame changed only in `data-params`, in `data-attributes` and in the `style` of its box and the new parameters equal the values that the component shows, which are the current values of its bar. The page script then sets the new `data-params`, `data-attributes` and box style on the frame, the bar takes the new values as its Markdown values, and the frame and the block around it are not highlighted. This is what happens after Write to file. The `source` region is replaced after a write as after any save, so `bake/copy` copies the written line. A frame whose new parameters differ is replaced, and its component starts again. Every bar keeps its unsaved values and its message, keyed by the path of the article, the name of its component and the position of the frame among the frames of that component on the page, so a save that adds lines above the component keeps them. A bar that an update in place recreates after `bake:content` shows them again and gives the values to the restarted component. The unsaved values are also stored in `sessionStorage` as `bake-dev-param-values`, so they stay after a reload of the tab. A bar restores only the stored values that the current declaration of its component accepts, by type, `options`, `min` and `max`, and the page drops the stored entries of its article whose component it no longer shows.

The bar has three buttons, in this order: Reset, Copy and Write to file, which is the filled primary button on the right. Write to file sends `POST /__bake/params` with `{ file, version, line, name, params, write: true }`, and the server rewrites the line in the `index.md`; Copy sends the same request with `write: false` and puts the returned line on the clipboard; Reset goes back to the values in the Markdown. Nothing is written without the button. The server accepts only requests whose `x-bake-token` header holds the token from `data-token` and answers 403 otherwise, whether the request has an `Origin` header or not, because the file name, the version and the line are visible to anyone who can open the page. It also accepts only requests with the content type `application/json` and, when the request has an `Origin` header, only requests whose origin has the host of the request, compared without regard to letter case; it answers 415 and 403 otherwise. It accepts only the `index.md` of an article that the preview serves and a component that the blog declares. It reads the file again, and when its SHA-256 hash differs from the version the page sent, it answers 409 with `<file> changed after this page was built; save it in your editor and try again`. Otherwise it rewrites the line with `rewriteSource` from `src/dev/params.js` and answers with the new line and the new version, which the page keeps for the next request. The bar shows each answer; a success message stays for 8 seconds or until the next action, an error stays until the next action, also across an update in place, and the watcher then rebuilds the page after a write as after any save. The check sees only what is saved on disk: changes that are still unsaved in the editor are not visible to the server, and saving the editor afterwards overwrites the written line. When the refusal and the update caused by the outside change arrive in either order, the bar ends with the message and its unsaved values, and the page has the new version, so the next Write to file succeeds.

`rewriteSource` changes only the `{…}` of the `:::name` line, which may follow indentation and blockquote markers, and refuses a line without it. Every parameter value is checked with the conversion and the checks of `src/components/declarations.js`, and a file parameter must name a file in the article folder. Only parameters whose new value differs from the value the line gives, written or default, are touched: a changed parameter whose new value is the default is removed, a changed attribute is replaced in place, and a new one is appended at the end. Every other attribute, including `width` and `height`, and every other character of the line stay as written. Each changed attribute is written by `writeAttribute` from `src/markdown/attributes.js`, which `writeAttributes` also uses for the attributes that copying writes. A boolean is written as its bare name when true and as `name=false` when false with the default true. A number is written as JavaScript's shortest form. Text made only of ASCII letters, digits and the characters `_.%/-` is written bare, other text in double quotes, text with `"` in single quotes, and text that contains both quote characters is refused. When no attribute remains, the braces are dropped.

The header of the problems list has a switch, Parameter bars, that hides and shows every bar. The choice is stored in `localStorage` as `bake-dev-param-bars`, and the bars are shown by default. The bars take their font and colours from the theme's CSS variables `--font-ui`, `--font-mono`, `--surface`, `--surface-2`, `--ink`, `--ink-2`, `--ink-3`, `--line`, `--line-2`, `--accent` and `--series-2`, which pass into the shadow root, with neutral light colours when a theme does not define them, so they follow the reader's theme setting. `switch.css` holds the switch that the bars and the problems list share, and each sets its colours. The state changes of the bars fade; the message under the controls also slides, except when the reader prefers reduced motion. A pressed button shrinks to 97 percent without a transition.

When a change replaces a block and an element inside it with the same `data-line`, such as a component frame inside its block, only the outermost element is highlighted. Double-clicking inside a parameter bar does not open VS Code.

## Error reports

Every problem Bake finds in a blog is reported as one line:

```
content/posts/llm/rope/index.md:3:7 URL /2026-10/rope/ is already used by content/posts/2026-10/rope/index.md
```

The format is `file:line:col message`, with the path relative to the blog root and the message in English. Bake runs every check before it reports, so one run lists all problems, sorted by file, line and column, followed by a count such as `1 error, dist/ was not written`. Articles are checked against the settings in `bake.config.js`, so when `bake.config.js` has errors, Bake reports those and does not check the articles. A build with errors writes nothing and leaves an existing `dist/` unchanged. A build without errors writes into `.dist-staging/` in the blog root and then replaces `dist/` with it, so `dist/` never holds a partly written site or files from an earlier build. Every build first removes `.dist-staging/` and `.dist-previous/` left by an interrupted build. `bake dev` shows the same lines in the terminal and on the page.

## Libraries

- Use mature libraries for general problems: Markdown parsing, math typesetting, syntax highlighting, diffing, sanitizing and validation.
- Write Bake's own core pieces by hand: the article structure, the theme interface, the component contract, the dev server's page updates and copying as Markdown.
- When switching to a library, accept its native behavior. Do not wrap it to reproduce the quirks of the code it replaces.
- Add a dependency only in the change that uses it, and pin the npm major version given in `package.json` when regenerating the lock file.
- Markdown is parsed by remark with GFM, math, front matter and `remark-cjk-friendly`, which lets emphasis close next to Chinese punctuation. `REMARK_PLUGINS` in `src/markdown/remark-plugins.js` lists GFM, math, `remark-cjk-friendly` and `remark-cjk-friendly-gfm-strikethrough` with their options, and both the article parser in `src/markdown/article.js` and the chat answer renderer use that list; the article parser adds front matter and Bake's own syntax. Bake's own syntax is written as micromark extensions in `src/markdown/`: `\eqref{label}` in text, `:::` blocks (remark-directive does not accept a block without a name such as `:::{width=wide}`, and its text directives would read `\eqref{eq:ffn}` as a directive), `==highlight==` with the same CJK rules that `remark-cjk-friendly-gfm-strikethrough` uses for `~~`, `[@key]` citations, and footnote references without a definition, which GFM would otherwise leave as plain text. A `:::` line inside a fenced code block does not close the block around the code; the `:::` tokenizer reads a code fence as CommonMark does, as a line of three or more backticks or tildes with at most three spaces of indentation, so indented code that starts with backticks is not a fence. Before parsing, `src/markdown/table-math.js` replaces each `|` inside `$…$` on a line that holds a `|` and a `$` with a character from the private use area U+E000 to U+F8FF that the article does not contain, because GFM splits table cells before it reads math. After parsing it turns that character back into `|` in every string field of every node, such as the text, the info string of a `:::` block and the title of a link, so a private-use character that the article itself contains is published unchanged. An article that contains every character of that area and needs one is reported at the first such line.
- Copying writes Markdown with mdast-util-to-markdown and the serializer extensions of the same syntax: `gfmToMarkdown` from `mdast-util-gfm`, `mathToMarkdown` from `mdast-util-math`, `mdast-util-to-markdown-cjk-friendly` and `mdast-util-to-markdown-cjk-friendly-gfm-strikethrough`. `serializeMarkdown` in `src/markdown/serialize.js` adds Bake's serializer extensions for highlights, citations, equation references and `:::` blocks, which each syntax module exports next to its micromark extension, writes the attributes of headings, images and `:::` blocks with `writeAttributes` from `src/markdown/attributes.js`, which writes them in a form that `parseAttributes` reads back to the same values, and writes `verbatim` nodes unchanged. The serializer is part of the selection chunk of `bake/copy`, so the page script of a theme does not hold it.
- Raw HTML in an article is parsed once by `hast-util-from-html` in `src/markdown/raw-html.js`. The parsed elements give the ids that links can point to, the addresses in `srcset` and in the URL attributes that `html-url-attributes` lists, which decide `keepSource`, and the positions of the `id` attributes that embedded and previewed content leaves out; the raw HTML itself is published as written.
- Math is typeset by MathJax 4 (`@mathjax/src`) into SVG with the New Computer Modern font. Each article is typeset in its own MathJax document, so macros defined in one article do not reach another, and every formula is compiled twice so that `\eqref` can refer to a later label. Equations are numbered by MathJax's AMS numbering with the TeX package `bake` that `src/render/math.js` defines. Its tag class numbers a display formula that has a `\label` outside every numbered environment in the same way as an `equation` environment, so `\tag` replaces its number and `\notag` removes it. Its macros for `\label`, `\ref` and `\eqref` record each label and reference that MathJax reads and then run MathJax's own commands, so the build checks exactly the commands that MathJax typesets, and a command inside a TeX comment is neither numbered nor checked.
- Code is highlighted by Shiki with a theme created by `createCssVariablesTheme`, so the colors are CSS variables that themes and dark mode set.
- Images are read and converted by sharp. sharp reports an AVIF image as the format `heif` with the compression `av1`, and `readImage` in `src/render/images.js` treats exactly that combination as AVIF; other HEIF images are not accepted. Size values such as `560px` and `70%` are parsed by `parseSize` and checked by `sizeProblem` in `src/config/rules.js`, which every syntax with a pixel or percent size uses.
- The media type of a served or published file comes from `mime` through `contentType` in `src/content-types.js`, which adds the UTF-8 charset to `text/` types. The column width of a character in a code block comes from `get-east-asian-width`, and the word count counts every character of `\p{Script=Han}` as one word.
- Text that Bake writes into HTML or XML by hand, in the feed, the sitemap, the share card and the pages that `bake dev` generates, is escaped by `stringify-entities` through `escapeMarkup` in `src/escape.js`.
- Themes are compiled by Vite with `vite-plugin-solid`, and their page structure and page scripts are written with SolidJS.
- The essay theme self-hosts LXGW WenKai from `lxgw-wenkai-webfont`, whose stylesheet splits the font into files by character range so that a page only downloads the files for the characters it shows, and JetBrains Mono from `@fontsource/jetbrains-mono`.
- Share images are drawn and browser tests run with Playwright, pinned to the exact version that matches the Chromium preinstalled in the cloud environment. `playwright` is a dependency of Bake, and `bake build` needs Playwright's Chromium, installed with `npx playwright install chromium`, when a card has to be drawn.
- `bake dev` uses Node's `http` module, Server-Sent Events and `fs.watch` with `recursive: true` and `node:crypto` for the source version, and needs no dependency of its own.

## Clean code

- The only compatibility code allowed is one migration step that upgrades old data files to the current format. There are no shims, fallbacks, legacy aliases or dual code paths.
- Fix root causes and replace old behavior outright. Code that is no longer used is deleted; git history keeps it.
- A known performance gap is written down here together with who accepted it.
- Drawing share images makes `npm test` about 30 seconds slower on the development machine, 81 seconds against 51 seconds without share images, because every unit test that runs `bake build` on a blog with articles launches Chromium. Accepted by the coordinator on 2026-10-19.
- The AI chat bundle has its own copies of `solid-js` and MathJax, so a page with components and math loads them twice when the reader opens the chat and an answer has a formula. Sharing them with the component bundle would make the chat build depend on each blog. Accepted by the coordinator on 2026-10-19.
- Copying as Markdown loads the selection chunk of `bake/copy` only when the reader starts a selection in the article, opens a context menu in it or presses a key together with Meta or Control, so a page on which the reader copies nothing loads only the page script. The chunk holds mdast-util-to-markdown with its GFM, math and CJK extensions and the code that converts a selection: 66.6 KB, 21.9 KB with gzip, in the essay and in the bento theme. The page scripts hold none of it, so the essay page script is 67.7 KB, 22.7 KB with gzip, and the bento page script 41.6 KB, 15.3 KB with gzip, where they were 80.2 KB and 54.1 KB, 26.7 KB and 19.2 KB with gzip, while copying wrote Markdown by hand. The AI chat has its own selection chunk, 30.4 KB and 10.2 KB with gzip, which its panel imports when the reader asks about a selected passage. A copy before the chunk has loaded waits for the chunk, as described in "What a theme writes for copying". Accepted by the coordinator on 2026-10-20.
