# Contributing

Bake is being rebuilt from scratch to follow the redesign. This file holds the architecture rules every change must respect. When a rule can be checked by a test, the test is named next to it; new rules are added here.

## Tool and blog are separate

This repository contains only the tool: the CLI, the Markdown pipeline, the built-in themes and the optional component kit. Posts, components, custom themes and site settings live in the blog's own repository. Bake never assumes a particular blog. `examples/blog/` is the only blog in this repository: it holds the syntax article that lists every syntax item, serves as the source of the tutorial, and is the integration test fixture. Unit tests that need other blogs, such as error cases, create them in temporary directories.

## Planned layout

The layout grows task by task. Today `src/cli.js`, `src/report.js`, `src/config/`, `src/markdown/`, `src/build/`, `src/render/`, `src/dev/` and `src/themes/essay/` exist. `src/config/` reads `bake.config.js`, front matter and `preamble.sty`, `src/markdown/` parses the article body into the article structure, `src/render/` typesets math, highlights code, reads and converts images and turns Markdown nodes into HTML, `src/build/` reads the blog, resolves the links between articles, compiles the themes, renders the pages, the homepage and the 404 page, writes the RSS feed and the sitemap, draws the share images and writes `dist/`, `src/dev/` serves the pages for `bake dev` and updates them on save, and `src/themes/essay/` is the essay theme.

|---|---|
| `src/cli.js` | Command entry: `bake new`, `bake dev`, `bake build` |
| `src/report.js` | Error records and the `file:line:col message` lines printed for them |

## Themes interpret, they never add syntax

The set of things an article can write (heading levels, blocks, width levels `body`, `wide` and `page`, front matter fields) is defined by Bake alone. A theme receives the parsed article and decides how to lay it out; it cannot add attributes, blocks or front matter fields. An attribute no theme knows is a build error. Adding syntax means changing Bake's syntax table and stating what it means in every theme.

## The article structure

The article structure is the interface between Bake and the themes. Bake builds it in two steps, because links and embeds refer to other articles. `readArticle(file, source, errors, { folder, preamble, url })` in `src/markdown/article.js` parses one `index.md`, typesets its math and reads its images; it is asynchronous for that reason. `folder` is `{ path, files }` of the article folder, which images are resolved against, `preamble` holds the definitions read from `preamble.sty` by `src/config/preamble.js`, and `url` is the address of the article, `/YYYY-MM/slug/`. When every article has been read, `indexPages(pages)` in `src/build/links.js` indexes them by address, `link(index, errors)` on each article checks its links and `:::embed` blocks against that index, and `structure()` returns the article structure. `link` reports its problems and those of the following `structure()` call into `errors` and replaces the result of an earlier `link`, so the two steps can run again on a parsed article when other articles change. `parseArticle(file, source, errors, options)` runs the steps for a single article whose links can only point to itself. The front matter is read separately by `src/config/front-matter.js`. Every `html` value is an HTML fragment that a theme inserts unchanged.

| Field | Contents |
|---|---|
| `intro` | The blocks before the first `##` heading. |
| `sections` | One entry per `##` heading: `id`, `number` (`01`, `02` and so on), `title` (HTML), `text` (plain text), `toc` (the title for the table of contents, from `{toc="…"}` or the heading text), `width` (`body`, `wide`, `page` or undefined), `line`, `recap` (HTML, when the section has a `:::recap` before its first `###` heading), `blocks` and `subsections`. |
| `subsections` | One entry per `###` heading in the section: `id`, `title`, `text`, `toc`, `line` and `recap`. |
| `toc` | The table of contents: for each section `id`, `number`, `title`, `recap` and `children`, and for each `###` heading in `children` its `id`, `title` and `recap`. The titles are plain text. |
| `sidenotes` | The footnotes, numbered by their first reference: `number`, `id` (`sidenote-1`), `line` of the definition and `html`. |
| `references` | The entries of `:::references`, numbered by their first citation: `key`, `number`, `id` (`reference-key`) and `html`. Entries the article never cites follow the cited ones and have no `number`. |
| `previews` | One entry per target of the internal links on the page, including links and citations inside embedded content, for the preview card: `target` (the address of the article followed by the decoded anchor, such as `/2026-10/rope/#angles`), `href` (the address relative to the page), `kind`, `article` (the title of the target article), `number`, `title` and `html`. For a `reference` entry, `number` is the citation number of the entry in its article (undefined for an entry that is never cited) and `html` is the entry. For a `section` entry, `number` is the number of the section that holds the target, such as `3` or `3.2` for its second `###` heading, undefined before the first `##` heading and for a whole article; `title` is the HTML of the target heading, or of the heading of the section that holds any other target, undefined for a whole article; `html` holds at most three blocks after a target heading or at the start of a whole article, ending before the next heading, the target paragraph, the display formula of a target equation, or the content of a target sidenote. |
| `words` | The length of the article: every Chinese character and every other word of the text and inline code counts as one. Code blocks, math, sidenotes and embedded content are not counted. |
| `images` | The images that the build converts to WebP: `source` (the path in the article folder), `path` (the published path), `width`, `lossless` and `keepSource`, which is true when a link, raw HTML or a component attribute in the article refers to the original file so that it is published too. Images published unchanged are copied with the other files of the folder. |
| `image` | The published path in the article folder of the first image in reading order, with sidenotes read where they are referenced: the WebP path for a converted image and the original path for an image published unchanged. Undefined when the article has no image. |
| `glyphs` | When the page has math: an HTML fragment with a hidden `<svg>` that holds the glyph paths of every formula in the article and of the formulas in its embeds and previews. Formulas refer to these paths, so the page includes the fragment once, together with the MathJax styles. MathJax names each path after the font, the variant and the character, so the paths of formulas from different articles combine into one fragment. |

A block has `type`, `line`, `endLine` and `html`. The type is the mdast node type (`paragraph`, `heading`, `list`, `blockquote`, `code`, `math`, `table`, `html`, `thematicBreak`), `figure` for an image on its own line, the name of a built-in block (`aside`, `fold`, `references`, `example`, `list-table`, `embed`) or `component`. A block wrapped in `:::{width=…}` has `width`. A block whose natural width Bake knows at build time has `naturalWidth`, a CSS length that the theme or page script compares with the column to place the block automatically: the formula width in `ex` for display math, the longest line in `ch` for code, with East Asian wide characters counted as two, and the written width for a figure whose size is set in pixels. A figure without a size or with a percentage size has no `naturalWidth` and stays inside the text column, however wide its image file is. Tables and components have no `naturalWidth`; the page measures them. A paragraph that ends with `^name` and a heading have `id`. A `###` or deeper heading also has `depth`, `title`, `text` and `toc`. A component has `name` and `attributes`. Headings inside other blocks do not start sections, and a `:::recap` inside another block stays in that block's HTML as `<div class="recap">`.

Embedded and previewed content comes from another article, so Bake renders it differently from the article's own content: headings, paragraphs, reference list items and raw HTML elements have no `id`, equations keep their numbers but lose their ids, sidenote numbers are left out, and links to anchors of the source article, citations, equation references and relative image addresses point into the source article. A link to an anchor of the source article becomes an internal link, and a citation has `data-target` with the address of its entry, so the preview card shows the entry of the source article. A preview shows the content of a component as `<div class="component-caption">` in place of the component.

The HTML marks the parts a theme styles or moves:

| Part | HTML |
|---|---|
| Sidenote number | `<sup class="sidenote-ref" data-sidenote="1"><a href="#sidenote-1">1</a></sup>` |
| Citation | `<a class="citation" href="#reference-key">[1]</a>` |
| Highlight | `<mark>` |
| Quote with a source | `<figure class="quote">` holding the `<blockquote>` and a `<figcaption>` |
| Aside | `<aside class="aside">`, with `<p class="aside-title">` when it has a title |
| Fold | `<details class="fold">` with the title in `<summary>` |
| Reference list | `<ol class="references">` with one `<li id="reference-key" value="1">` per cited entry, followed by `<ul class="references uncited">` with one `<li id="reference-key">` per uncited entry |
| Width inside another block | `<div data-width="wide">` |
| Internal link | `<a class="internal-link" href="../../2026-10/rope/#angles" data-target="/2026-10/rope/#angles">`, with the address relative to the page; `data-target` names the entry of `previews` and is missing when the target is an article published from an HTML file. The anchor may name a heading, a paragraph anchor, a sidenote, a reference entry or an equation of the target article. |
| Embed | `<div class="embed">` holding one `<div class="embed-part">` per address, each ending with `<p class="embed-source"><a href="…"><cite>Article title</cite><span class="embed-number">3.2</span></a></p>`; the number is missing for content before the first `##` heading |
| `:::embed` inside embedded or previewed content | One `<p class="embed-link">` per address, holding an internal link whose text is the title of the target heading or article |
| Block that a later task renders (components) | `<div data-block="name">` around its content |
| Math | `<mjx-container class="MathJax" jax="SVG" data-tex="…">` holding an SVG, with `display="true"` for a display formula. The styles from `mathStyles()` in `src/render/math.js` lay it out. |
| Numbered equation | `id` on the element MathJax generates for the equation number: the label name for a labeled equation and `eq-` plus the number, such as `eq-2`, otherwise |
| Equation reference | `<a class="eqref" href="#label">(1)</a>`, with the label percent-encoded in `href` |
| Code | `<pre class="shiki bake" data-language="python">` with `<span>` colors that use the `--code-…` CSS variables |
| Table | `<div class="table-scroll">` around the `<table>`, so a wide table scrolls horizontally |
| List table | `<div class="table-scroll">` around `<table class="list-table">` with a `<thead>` row and `<tbody>` rows |
| Image | `<img>` with `width`, `height`, `loading="lazy"` and `decoding="async"`; an inline image also has `style` with its width when the article sets a size |
| Figure | `<figure class="figure">` holding the `<img>` and a `<figcaption>`, with `style="width:560px"` when the article sets a size and `data-float="left"` or `data-float="right"` when it sets `float`. The theme makes the image fill the figure and centres the figure in the column. |
| Example | `<div class="example">` holding `<div class="example-source">` with the highlighted Markdown and `<div class="example-result">` with the rendered content |

## Themes

A theme is a folder with five entry files. `page.jsx` default-exports a SolidJS component that returns the whole `<html>` element of an article page; `home.jsx` default-exports a SolidJS component that returns the whole `<html>` element of the homepage; `not-found.jsx` default-exports a SolidJS component that returns the whole `<html>` element of the 404 page; `client.jsx` is the page script of these pages and imports the theme's stylesheets, fonts and other files; `theme.css` is the stylesheet that plain HTML pages can link to get the theme's fonts, colours and dark mode. Every theme needs `page.jsx` and `client.jsx`. The site theme, `theme` in `bake.config.js`, also needs `home.jsx`, `not-found.jsx` and `theme.css`; a theme that only articles choose does not. The built-in themes live in `src/themes/`. A blog adds a theme with a folder `themes/<name>/`, and replaces single files of a built-in theme with files of the same relative path in a folder of the same name, such as `themes/essay/header.jsx`; every relative import inside a theme folder, including an `@import` in a stylesheet, is looked up in the blog's folder first and in the built-in folder second. A theme imports `solid-js` from Bake, so a blog does not install it.

`src/build/theme.js` compiles the site theme and each theme that a published article uses with Vite and `vite-plugin-solid`. The site theme is compiled even when the blog has no articles, because the homepage and the 404 page are always written. `page.jsx`, and for the site theme `home.jsx` and `not-found.jsx`, are compiled together for the server into one module that exports `render` for article pages, `renderHome` for the homepage and `renderNotFound` for the 404 page, and are rendered to static HTML with Solid's `renderToString`, without hydration. `client.jsx` is compiled into one classic script and one stylesheet, which together with the fonts and images they refer to are written to `dist/assets/` under names that contain a content hash. The `theme.css` of the site theme is compiled in a separate Vite build to `dist/_bake/theme.css`; its fonts and images are written to `dist/assets/` like those of `client.jsx`, and its `url()` addresses are relative to `dist/_bake/`. A theme that cannot be compiled is reported at the file and position of the error, an article that the theme throws on is reported at the article, and a homepage or a 404 page that the site theme throws on is reported at the theme folder.

The site files are written by `src/build/site-files.js` and `src/build/site.js`, and every address in them is absolute, built from `url` in `bake.config.js` with a slash added at its end, so `https://x.github.io/bake` gives `https://x.github.io/bake/2026-10/rope/`. Drafts never appear in them, also in `bake dev`, where drafts have pages.

| File | Contents |
|---|---|
| `dist/index.html` | The homepage. |
| `dist/404.html` | The 404 page, which GitHub Pages serves at every address without a file. |
| `dist/feed.xml` | An RSS 2.0 feed with an `atom:link` to itself. The channel has the site title, the address of the homepage, `description` from `bake.config.js` or the site title when it is not set, and the language. Each published article and plain HTML page is one `item`, in the order of the homepage, with `title`, `link`, `guid` (the same address, marked as a permalink), `pubDate` (midnight UTC of the date), `category` (the category name, when set) and `description` (the summary, when set; never the article text). The feed has no build time, so the same blog always gives the same file. |
| `dist/sitemap.xml` | A sitemap with one `<loc>` for the homepage and for each published article and plain HTML page. |
| `dist/og/YYYY-MM/slug-hash.png` | The share image of each published article and plain HTML page that is not a draft, described in "Share images" below. |
| `dist/_bake/theme.css` | The compiled `theme.css` of the site theme. A plain HTML page links it with `<link rel="stylesheet" href="../../_bake/theme.css">`, which works in `bake dev` and at any address the site is served from; the absolute form `/_bake/theme.css` works only when the site is served at the root of its domain. The page is still published byte for byte. |

A file in `public/` that would be written to one of these addresses, or to any address in `dist/_bake/` or `dist/og/` or to a file the themes write to `dist/assets/`, is reported as a conflict.

### Share images

`bake build` publishes one share image for every published article and plain HTML page that is not a draft, and the essay theme names it in the `og:image` tags of the article page. `src/build/share-images.js` plans and draws the images, and `src/build/share-card.js` holds the HTML template of the card.

When the front matter has `cover`, the cover file is published unchanged as the share image at `og/YYYY-MM/slug-hash.ext`, where `hash` is the first 12 hexadecimal digits of the SHA-256 of the file and `ext` is the extension of the cover in lower case. The cover must be a PNG, JPEG, GIF, WebP, AVIF or SVG image; Bake reads its size with sharp for `og:image:width` and `og:image:height` and reports a cover it cannot read at the `cover` field, in `bake dev` too.

Otherwise Bake draws a 1200 by 630 pixel PNG card and publishes it at `og/YYYY-MM/slug-hash.png`. The card has a vertical strip on the left in the category colour, or in `--accent` when the article has no category, a line with the site title and the category name, the title in bold, the summary below it, and on the right the first frame of the article's `preview` in a 16:9 frame. Without a preview the text takes the whole width. The card page links the compiled `theme.css` of the site theme with `data-theme="light"` on `<html>`, so it uses the fonts and the light colours of the site theme, and it uses these CSS variables of that stylesheet: `--bg`, `--ink`, `--ink-2`, `--ink-3`, `--accent`, `--line`, `--surface-2` and `--font-heading`. A site theme that does not define them gets a card with the browser's default colours and font.

The cards are drawn in Chromium through Playwright. `bake build` launches one browser only when at least one card has to be drawn, and draws the cards in four pages at a time. Each page loads the card from an address that only exists inside the browser, and Playwright answers every request from memory: the card, the files of the site theme and the files of the article folder. Every other request is refused, so drawing a card needs no network. The page imports the preview module, calls its default export with the empty element of the frame, checks that it returns `start` and `stop` like the homepage does, waits for the fonts and two animation frames, and takes the screenshot; `start` is never called. A preview that throws, fails to load, returns something else or does not finish within 10 seconds is reported at the `preview` field of the front matter. When Chromium cannot be launched, the build reports one error at the first article that needs a card, with Playwright's reason and the command `npx playwright install chromium`. Like every other error, these errors leave `dist/` unchanged.

The hash in the name of a card covers every input of the drawing: the card template, the Playwright version, the site language and title, the category name and colour, the title, the summary, the path of the preview, the compiled `theme.css` of the site theme, which names its font files by their content hash, and, when the article has a preview, the path and content of every file in the article folder except `index.md`, so a change to any module that the preview imports gives a new name. When `dist/` already holds a file with the name of a card, `bake build` copies that file into the new `dist/` and does not draw the card again, so a build in which no card changed does not launch Chromium. Bake keeps no other cache.

`createSite(root, { shareImages: true })` plans the share images, and only `bake build` sets it. `bake dev` draws no share images, so its pages have no `og:image` tags. Plain HTML pages are published byte for byte, so they get a share image file but no tags; their author can write the tags into the page.

The page component receives these props:

| Prop | Contents |
|---|---|
| `site` | `title`, `url`, `language` and `description` from `bake.config.js`, where `description` is undefined when it is not set, and `link`, the absolute address of the homepage, which always ends with `/`. |
| `article` | `title`, `summary`, `date`, `tags` (a list, empty when not set), `category`, `draft`, `toc` (the table of contents style of the article or the site), `url`, `link` (the absolute address of the article, such as `https://example.com/2026-10/rope/`), `shareImage` (`{ link, width, height }` with the absolute address and the size of the share image, undefined in `bake dev`), `words` and `content`, the article structure described above. |
| `assets` | `root`, the relative path from the page to the site root such as `../../`; `styles` and `scripts`, the paths of the compiled stylesheet and script relative to the page; `mathStyles`, the MathJax stylesheet when the article has math. |

The homepage component receives these props:

| Prop | Contents |
|---|---|
| `site` | The same as for an article page. |
| `home` | `groupBy` (`category` or `month`), `columns` (3, 4 or 5) and `categories`, the list of `{ id, name, color, desc }` from `bake.config.js` in the order written there. |
| `articles` | The published articles, newest first and by title within a day. Each entry has `title`, `summary`, `date`, `tags` (a list), `category` (the category object from `bake.config.js`, or undefined), `draft`, `url` (relative to the site root, such as `2026-10/rope/`), `preview` (the path of the article's `preview` file relative to the site root, or undefined) and `image` (the article structure's `image` relative to the site root, or undefined; plain HTML pages have none). Markdown articles and plain HTML pages have the same fields. |
| `assets` | `root`, which is `./`, and `styles` and `scripts`, the paths of the compiled stylesheet and script relative to the homepage. |

The 404 page component receives these props:

| Prop | Contents |
|---|---|
| `site` | The same as for an article page. |
| `articles` | The published articles and plain HTML pages that are not drafts, in the order of the homepage. Each entry has `title` and `url` (relative to the site root, such as `2026-10/rope/`). |
| `assets` | `root`, the absolute path of the site root, taken from the path of `url` in `bake.config.js`: `/` for `https://example.github.io` and `/bake/` for `https://x.github.io/bake`; `styles` and `scripts`, the paths of the compiled stylesheet and script starting with `root`. The 404 page is served at addresses of any depth, so its paths cannot be relative. |

A `preview` file is an ES module whose default export is a function that receives an empty element covering the card's 16:9 frame, draws the first frame of an animation into it and returns `{ start(), stop() }`. The function is called once for every card that shows the article, so it keeps its state inside the call. Colours come from the theme's CSS variables, so the preview follows dark mode.

### What a theme writes for bake dev

`bake dev` updates an open page without reloading it when only the article body changed. A theme supports this with three attributes and one event, and the same HTML is published by `bake build`:

| Part | Meaning |
|---|---|
| `data-region="name"` | An element whose content comes from the article body, such as the article text, the table of contents or the word count. Each name appears once in the HTML that the theme renders. |
| `data-line="12"` | An element inside a region that shows one part of the article structure, with the `line` of that part: a block, a heading or a sidenote. |
| `bake:content` | The event that `bake dev` dispatches on `document` after it has replaced the content of the regions. |

After a save, the page script of `bake dev` loads the new HTML of the page. When the new page differs from the old one only inside regions, it replaces the children of every element with that `data-region` value, including copies that page scripts made, and dispatches `bake:content`. Otherwise it reloads the page. A page script that keeps references to elements inside a region reads them again on `bake:content`. An element with `data-line` whose HTML is not in the old page counts as changed: it is highlighted, and when it is off screen a notice names the `##` or `###` section of its line. Double-clicking an element with `data-line` opens `vscode://file/<path of the index.md>:<line>:1`. A theme without these attributes still works in `bake dev`; its pages reload on every save.

### The essay theme

`home.jsx` writes the homepage: the site title and description, a bar that stays at the top of the screen with the chips and the switches, and the cards. When the blog has no published articles, the homepage has no bar and shows one line that says there are no posts yet. It renders the grouping by category (when at least one category has a published article) and the grouping by month, and `data-group` on `<html>` selects the one that is shown, so a reader without scripts sees the default grouping, and the category chips still work as links to their groups. `data-columns` on `<html>` sets 3, 4 or 5 card columns from 1000 pixels up; below 1000 pixels the cards fill the width with a minimum width of 290 pixels. Below 600 pixels the chips take a full line of the bar and the switches go on the line below. Titles and summaries break long words so that they stay inside the card. A card shows the article's preview, its first image when it has no preview, or a block in the category colour with the title when it has neither, and its border takes the category colour, or the accent colour when no categories are set, while the pointer rests on it. `not-found.jsx` writes the 404 page: the site title as a link to the homepage, a heading that says the page does not exist, the requested address, a list of articles that the reader may be looking for and a link back to the homepage. The page holds every entry of `articles` as a hidden list item with `data-url`; `not-found.js` shows the requested address and the entries whose slug equals the last segment of the address and whose address differs from it, which finds an article whose `date` changed and moved it to another month. A reader without scripts sees the heading and the link to the homepage. `meta.jsx` writes the tags of the document head that the article page and the homepage share: `<link rel="canonical">` and `og:url` with the absolute address (`article.link` or `site.link`), a `<link rel="alternate" type="application/rss+xml">` to `feed.xml`, `og:type` (`article` or `website`), `og:title`, `og:description` (the summary of the article or the description of the site, when set), `og:site_name`, `og:locale` (the site language with `_` in place of `-`), `twitter:card` set to `summary_large_image`, and on an article page with `article.shareImage` the tags `og:image`, `og:image:width`, `og:image:height` and `twitter:image`. `theme.css` imports `styles/fonts.css` and `styles/tokens.css` and sets the background, the text colour and the fonts of the body, so a plain HTML page that links it follows the system colour scheme and `data-theme` on its `<html>`. `page.jsx` writes the document head of an article page, `header.jsx` the masthead, `toc.jsx` the table of contents, `article.jsx` the body and `previews.jsx` one `<template class="bk-preview-template" data-target="…" data-kind="link">` per entry of `previews`, holding the card content, with `data-kind="reference"` and the layout of the citation card for a `reference` entry. Every block of the article structure is wrapped in `<div class="bk-block" data-type="…" data-line="…">`; blocks that can be wider than the text also have `data-width` (`body`, `wide`, `page`, or `auto` when the article sets no width) and the natural width as `--natural-width`. Each sidenote is rendered once, after the top-level block that first refers to it, as `<aside class="bk-sidenote" data-sidenote="1" data-line="…">`, and headings have `data-line` too. An embed is one block with the `data-line` of its `:::embed` line; the embedded content inside it has no `data-line`, because its lines belong to another article. The regions are `article` on `<article class="bk-article">`, `toc` on the list of the table of contents, `words` on the word count, `glyphs` on the hidden MathJax glyphs and `previews` on the `<div class="bk-previews">` that holds the preview templates. UI text comes from `labels.js`, in Chinese when the site language starts with `zh` and in English otherwise. The words around the source line of an embed, such as 出自《…》, are set by `page.jsx` from `labels.js` as the CSS variables `--bk-embed-source-before` and `--bk-embed-source-after`, because that line is part of the HTML Bake generates.

The styles are in `styles/`. `tokens.css` defines every colour as a CSS variable, for the light and the dark theme, and `page.css` defines the column widths as variables for each breakpoint: 1340 pixels and up, 1000 to 1339 pixels, and below 1000 pixels. The page scripts are in `scripts/`, and `client.jsx` starts them:

| Script | What it does |
|---|---|
| `widths.js` | Gives every block with `data-width="auto"` the width `wide` when its content is wider than the text column and the screen has a wide level, and `body` otherwise, and writes the result to `data-resolved` on every block with `data-width`. |
| `notes.js` | From 1000 pixels up, copies each sidenote into the notes column next to the line of its number and moves it below any block that reaches into the column. Below 1000 pixels, a tap on a number opens the sidenote under its block. Hovering a number or a note highlights both. |
| `folds.js` | Animates opening and closing `:::fold` blocks, and opens every fold for printing. |
| `heading-links.jsx` | Copies the link of a heading when its `#` is clicked, and scrolls to the target of an in-page link after opening the folds around it. |
| `preview-card.jsx` | Shows one card for citations and internal links on devices that can hover with a fine pointer: the reference entry of a citation from 1000 pixels up, and the template of an internal link at every width. A citation that points to another article, such as one inside an embed, shows the template of that article's entry. The card appears 300 milliseconds after the pointer rests on a link, below the link and inside the viewport, switches to another link at once while it is shown or within 600 milliseconds after it hid, stays while the pointer is in it and hides 200 milliseconds after the pointer leaves. Keyboard focus on a link shows its card at once, moving the focus away hides it, and Escape hides it. A click on the card of an internal link opens the target. |
| `toc.js`, `drawer.jsx` | Marks the read, current and following entries of the table of contents from 1340 pixels up, and shows the table of contents in a drawer below that width. |
| `home.js` | On the homepage: loads the preview of each card of the visible grouping when the card comes near the screen and keeps the fallback when the preview fails; starts a preview while the pointer rests on its card or the card has focus, and on devices without hover while the card is in the middle tenth of the screen, and stops it while the card is off the screen; never starts one with reduced motion; switches the grouping and the column count and stores them; marks the category chip of the group on screen, and after a click on a chip keeps that chip marked until the scroll to its group ends; and filters the month grouping by tag. |
| `not-found.js` | On the 404 page: shows the requested address and the articles with the same slug at another address, as described above. |
| `settings.jsx` | The settings panel. Its rows come from `settingRows`; `chooseSetting(name, value)` applies and stores a choice and dispatches `bk:setting` on `document`. |

The reader settings are defined in `settings.js`: each setting has its values and its initial value, the choice is stored in `localStorage` as `bk-<name>`, and an inline script in the head sets `data-<name>` on `<html>` before the first paint. On the homepage the same script also applies the stored grouping and column count, `bk-group` and `bk-columns`, over the defaults that the page writes from `bake.config.js`. The homepage hides its switches and tag chips unless `data-script` is set. The same script sets `data-script` on `<html>`; the styles hide the sidenotes under their blocks only when it is set, so a reader without scripts sees every sidenote under the block that refers to it. Page scripts that change the layout dispatch the `bk:layout` event on `document`, and the scripts that measure the layout listen to it. `widths.js`, `notes.js` and `toc.js` read the blocks, sidenotes and headings again on `bake:content`, `preview-card.jsx` looks up the template of a link each time it shows a card and hides the card on `bake:content`, and the other scripts listen on `.bk-article` or `document` instead of on single elements, so they work on replaced content without changes.

## bake dev

`src/build/site.js` holds the steps that `bake build` and `bake dev` share. `createSite(root, { drafts, base, shareImages })` creates the state of one blog, where `drafts` set to true gives drafts a page and a card on the homepage, `base` replaces the path of `url` in `bake.config.js` as the root of the 404 page's assets and `shareImages` set to true plans the share images, and `updateSite(site, changedPaths)` reads it and renders every page: with `null` it reads everything, with a list of changed paths relative to the blog root it reads `bake.config.js` and `preamble.sty` again only when one of them or a file in `themes/` changed, parses again only the articles whose folder contains a changed path, and compiles a theme again only when a file in `themes/` changed or when the theme becomes or stops being the site theme, because only the site theme is compiled with `home.jsx`, `not-found.jsx` and `theme.css`. After reading, it links every article again, parsed again or not, because link errors, preview cards and embedded sections depend on other articles; linking and building the article structure take much less time than parsing. It returns the sorted errors, the articles, the pages with their outputs, the homepage output, the outputs of the 404 page, the feed and the sitemap, the theme files, the planned share images and the files of `public/`. `bake build` calls it once with `null`, copies or draws the share images with `shareImageOutputs` and writes the outputs with `writeDist`; `bake dev` keeps the state and calls it after every save.

`src/dev/watch.js` watches the blog root with `fs.watch` and `recursive: true`, ignores `dist/`, `node_modules/` and every file or folder whose name starts with a dot, and collects the paths of one save for 40 milliseconds. A path that does not exist and was not a known file before, such as a temporary file an editor writes and deletes during a save, is ignored. When the blog root can no longer be watched, because it was removed or the system has no file watches left, `bake dev` closes the server, prints `bake dev: cannot watch <root>: <reason>` and exits with status 1. `bake dev` does not reload the modules that `bake.config.js` imports; restart it after changing them.

`src/dev/preview.js` keeps the pages, the homepage, the 404 page, the feed and the sitemap that `bake dev` serves, in memory. It creates the site with `base` set to `/`, because `bake dev` serves the blog at the root of its address. When the errors include a file that is not an article, such as `bake.config.js` or a theme file, it keeps every page. Otherwise it takes the new pages of the articles without errors and keeps the last pages of the articles with errors. It compares the old and new pages: a page whose front matter changed, or that appeared or disappeared, is reloaded; a page whose HTML changed is updated in place; the homepage is reloaded when its HTML changed, which happens when the front matter of an article changes or an article appears or disappears; and a changed path that is not an article's `index.md` reloads every page.

`src/dev/server.js` serves the pages, the homepage at `/`, `/404.html`, `/feed.xml`, `/sitemap.xml` and `/_bake/theme.css` with Node's `http` module on port 4321 or the next free port, on every network interface. It adds `<script src="/__bake/client.js" data-bake-dev>` at the end of the body of every HTML page; on an article page the script carries the path of the `index.md` for VS Code, its path in the blog and the outline of `##` and `###` headings with their lines. `/__bake/events` is a Server-Sent Events stream with three events: `hello` with an id that changes when `bake dev` restarts, `problems` with the current problems, and `update` with the addresses to reload (`reload`, a list or `"all"`) and the addresses to update in place (`refresh`). Any address without a page answers 404 with the list of every article. `src/dev/client.js` is the page script: it keeps the HTML the page was loaded from, applies updates as described in "What a theme writes for bake dev", stores the scroll position in `sessionStorage` before a reload and restores it after, and shows the problems list and the notice in a shadow root styled by `src/dev/client.css`. The problems list opens when problems appear and closes when they are fixed. While the list is closed, a dot in the bottom right corner of the page takes its place: it is small and grey when there are no problems and red with the number of problems otherwise, and clicking it opens the list. The list, the dot and the notice fade and slide in and out with CSS transitions; when the reader prefers reduced motion, they only fade.

## Error reports

Every problem Bake finds in a blog is reported as one line:

```
content/posts/llm/rope/index.md:3:7 URL /2026-10/rope/ is already used by content/posts/2026-10/rope/index.md
```

The format is `file:line:col message`, with the path relative to the blog root and the message in English. Bake runs every check before it reports, so one run lists all problems, sorted by file, line and column, followed by a count such as `1 error, dist/ was not written`. Articles are checked against the settings in `bake.config.js`, so when `bake.config.js` has errors, Bake reports those and does not check the articles. A build with errors writes nothing and leaves an existing `dist/` unchanged. A build without errors writes into `.dist-staging/` in the blog root and then replaces `dist/` with it, so `dist/` never holds a partly written site or files from an earlier build. Every build first removes `.dist-staging/` and `.dist-previous/` left by an interrupted build. `bake dev` shows the same lines in the terminal and on the page.

## Libraries

- Use mature libraries for general problems: Markdown parsing, math typesetting, syntax highlighting, diffing, sanitizing and validation.
- Write Bake's own core pieces by hand: the article structure, the theme interface, the component contract and the dev server's page updates.
- When switching to a library, accept its native behavior. Do not wrap it to reproduce the quirks of the code it replaces.
- Add a dependency only in the change that uses it, and pin the npm major version given in `package.json` when regenerating the lock file.
- Markdown is parsed by remark with GFM, math, front matter and `remark-cjk-friendly`, which lets emphasis close next to Chinese punctuation. Bake's own syntax is written as micromark extensions in `src/markdown/`: `\eqref{label}` in text, `:::` blocks (remark-directive does not accept a block without a name such as `:::{width=wide}`, and its text directives would read `\eqref{eq:ffn}` as a directive), `==highlight==` with the same CJK rules that `remark-cjk-friendly-gfm-strikethrough` uses for `~~`, `[@key]` citations, and footnote references without a definition, which GFM would otherwise leave as plain text. Before parsing, `src/markdown/table-math.js` replaces each `|` inside `$…$` on a table line with a private-use character and restores it afterwards, because GFM splits cells before it reads math.
- Math is typeset by MathJax 4 (`@mathjax/src`) into SVG with the New Computer Modern font. Each article is typeset in its own MathJax document, so macros defined in one article do not reach another, and every formula is compiled twice so that `\eqref` can refer to a later label.
- Code is highlighted by Shiki with a theme created by `createCssVariablesTheme`, so the colors are CSS variables that themes and dark mode set.
- Images are read and converted by sharp. Size values such as `560px` and `70%` are parsed by `parseSize` and checked by `sizeProblem` in `src/config/rules.js`, which every syntax with a pixel or percent size uses.
- Themes are compiled by Vite with `vite-plugin-solid`, and their page structure and page scripts are written with SolidJS.
- The essay theme self-hosts LXGW WenKai from `lxgw-wenkai-webfont`, whose stylesheet splits the font into files by character range so that a page only downloads the files for the characters it shows, and JetBrains Mono from `@fontsource/jetbrains-mono`.
- Share images are drawn and browser tests run with Playwright, pinned to the exact version that matches the Chromium preinstalled in the cloud environment. `playwright` is a dependency of Bake, and `bake build` needs Playwright's Chromium, installed with `npx playwright install chromium`, when a card has to be drawn.
- `bake dev` uses Node's `http` module, Server-Sent Events and `fs.watch` with `recursive: true`, and needs no dependency of its own.

## Clean code

- The only compatibility code allowed is one migration step that upgrades old data files to the current format. There are no shims, fallbacks, legacy aliases or dual code paths.
- Fix root causes and replace old behavior outright. Code that is no longer used is deleted; git history keeps it.
- A known performance gap is written down here together with who accepted it.
