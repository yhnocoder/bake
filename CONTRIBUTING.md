# Contributing

Bake is being rebuilt from scratch to follow the redesign. This file holds the architecture rules every change must respect. When a rule can be checked by a test, the test is named next to it; new rules are added here.

## Tool and blog are separate

This repository contains only the tool: the CLI, the Markdown pipeline, the built-in themes and the optional component kit. Posts, components, custom themes and site settings live in the blog's own repository. Bake never assumes a particular blog. `examples/blog/` is the only blog in this repository: it holds the syntax article that lists every syntax item, serves as the source of the tutorial, and is the integration test fixture. Unit tests that need other blogs, such as error cases, create them in temporary directories.

## Planned layout

The layout grows task by task. Today `src/cli.js`, `src/report.js`, `src/config/`, `src/markdown/`, `src/build/`, `src/render/`, `src/components/`, `src/dev/` and `src/themes/essay/` exist. `src/config/` reads `bake.config.js`, front matter and `preamble.sty`, `src/markdown/` parses the article body into the article structure, `src/render/` typesets math, highlights code, reads and converts images and turns Markdown nodes into HTML, `src/components/` reads the components of a blog, checks their parameters and bundles them with the browser runtime, `src/build/` reads the blog, resolves the links between articles, compiles the themes, renders the pages and the homepage and writes `dist/`, `src/dev/` serves the pages for `bake dev` and updates them on save, and `src/themes/essay/` is the essay theme.

## Themes interpret, they never add syntax

The set of things an article can write (heading levels, blocks, width levels `body`, `wide` and `page`, front matter fields) is defined by Bake alone. A theme receives the parsed article and decides how to lay it out; it cannot add attributes, blocks or front matter fields. An attribute no theme knows is a build error. Adding syntax means changing Bake's syntax table and stating what it means in every theme.

## The article structure

The article structure is the interface between Bake and the themes. Bake builds it in two steps, because links and embeds refer to other articles. `readArticle(file, source, errors, { folder, preamble, url })` in `src/markdown/article.js` parses one `index.md`, typesets its math and reads its images; it is asynchronous for that reason. `folder` is `{ path, files }` of the article folder, which images are resolved against, `preamble` holds the definitions read from `preamble.sty` by `src/config/preamble.js`, and `url` is the address of the article, `/YYYY-MM/slug/`. When every article has been read, `indexPages(pages)` in `src/build/links.js` indexes them by address, `link(index, errors)` on each article checks its links and `:::embed` blocks against that index, and `structure()` returns the article structure. `link` reports its problems and those of the following `structure()` call into `errors` and replaces the result of an earlier `link`, so the two steps can run again on a parsed article when other articles change. `parseArticle(file, source, errors, options)` runs the steps for a single article whose links can only point to itself. The front matter is read separately by `src/config/front-matter.js`. Every `html` value is an HTML fragment that a theme inserts unchanged.

| Field | Contents |
|---|---|
| `intro` | The blocks before the first `##` heading. |
| `sections` | One entry per `##` heading: `id`, `number` (`01`, `02` and so on), `title` (HTML), `text` (plain text), `toc` (the title for the table of contents, from `{toc="…"}` or the heading text), `width` (`body`, `wide`, `page` or undefined), `line`, `recap` (HTML, when the section has a `:::recap` before its first `###` heading), `blocks` and `subsections`. |
| `subsections` | One entry per `###` heading in the section: `id`, `title`, `text`, `toc`, `line` and `recap`. |
| `toc` | The table of contents: for each section `id`, `number`, `title`, `recap` and `children`, and for each `###` heading in `children` its `id`, `title` and `recap`. The titles are plain text. |
| `sidenotes` | The footnotes, numbered by their first reference: `number`, `id` (`sidenote-1`), `line` of the definition and `html`. |
| `references` | The entries of `:::references`, numbered by their first citation: `key`, `number`, `id` (`reference-key`) and `html`. Entries the article never cites follow the cited ones and have no `number`. |
| `previews` | One entry per target of the internal links on the page, including links and citations inside embedded content, for the preview card: `target` (the address of the article followed by the decoded anchor, such as `/2026-10/rope/#angles`), `href` (the address relative to the page), `kind`, `article` (the title of the target article), `number`, `title` and `html`. For a `reference` entry, `number` is the citation number of the entry in its article (undefined for an entry that is never cited) and `html` is the entry. For a `section` entry, `number` is the number of the section that holds the target, such as `3` or `3.2` for its second `###` heading, undefined before the first `##` heading and for a whole article; `title` is the HTML of the target heading, or of the heading of the section that holds any other target, undefined for a whole article; `html` holds at most three blocks after a target heading or at the start of a whole article, ending before the next heading, the target paragraph, the display formula of a target equation, or the content of a target sidenote. |
| `words` | The length of the article: every Chinese character and every other word of the text and inline code counts as one. Code blocks, math, sidenotes and embedded content are not counted. |
| `images` | The images that the build converts to WebP: `source` (the path in the article folder), `path` (the published path), `width`, `lossless` and `keepSource`, which is true when a link, raw HTML or a component parameter in the article refers to the original file so that it is published too. Images published unchanged are copied with the other files of the folder. |
| `image` | The published path in the article folder of the first image in reading order, with sidenotes read where they are referenced: the WebP path for a converted image and the original path for an image published unchanged. Undefined when the article has no image. |
| `components` | The names of the components the page uses, sorted: the components of the article and of the content it embeds. A preview card shows no component, so previews add none. |
| `glyphs` | When the page has math: an HTML fragment with a hidden `<svg>` that holds the glyph paths of every formula in the article and of the formulas in its embeds and previews. Formulas refer to these paths, so the page includes the fragment once, together with the MathJax styles. MathJax names each path after the font, the variant and the character, so the paths of formulas from different articles combine into one fragment. |

A block has `type`, `line`, `endLine` and `html`. The type is the mdast node type (`paragraph`, `heading`, `list`, `blockquote`, `code`, `math`, `table`, `html`, `thematicBreak`), `figure` for an image on its own line, the name of a built-in block (`aside`, `fold`, `references`, `example`, `list-table`, `embed`) or `component`. A block wrapped in `:::{width=…}` has `width`. A block whose natural width Bake knows at build time has `naturalWidth`, a CSS length that the theme or page script compares with the column to place the block automatically: the formula width in `ex` for display math, the longest line in `ch` for code, with East Asian wide characters counted as two, and the written width for a figure or a component whose width is set in pixels. A figure without a size or with a percentage size has no `naturalWidth` and stays inside the text column, however wide its image file is. Tables have no `naturalWidth`; the page measures them. A component always has `width` or `naturalWidth`, so the page never measures it. A paragraph that ends with `^name` and a heading have `id`. A `###` or deeper heading also has `depth`, `title`, `text` and `toc`. A component has `name`, `attributes` (the attributes as written) and `params` (every declared parameter, converted to its type, with the defaults filled in), and `width` set from its `width` attribute or its `layout.width`, see Components below. Headings inside other blocks do not start sections, and a `:::recap` inside another block stays in that block's HTML as `<div class="recap">`.

Embedded and previewed content comes from another article, so Bake renders it differently from the article's own content: headings, paragraphs, reference list items and raw HTML elements have no `id`, equations keep their numbers but lose their ids, sidenote numbers are left out, and links to anchors of the source article, citations, equation references and relative image addresses point into the source article. A link to an anchor of the source article becomes an internal link, and a citation has `data-target` with the address of its entry, so the preview card shows the entry of the source article. A preview shows the caption of a component as `<div class="component-caption">` in place of the component. Embedded content shows a component with its frame, as its source article does, and the value of each `file` parameter points into the source article, such as `../../2026-10/rope/grid.json`, so the component loads the file that the source article publishes.

The HTML marks the parts a theme styles or moves:

| Part | HTML |
|---|---|
| Sidenote number | `<sup class="sidenote-ref" data-sidenote="1"><a href="#sidenote-1">1</a></sup>` |
| Citation | `<a class="citation" href="#reference-key">[1]</a>` |
| Highlight | `<mark>` |
| Quote with a source | `<figure class="quote">` holding the `<blockquote>` and a `<figcaption>` |
| Aside | `<aside class="aside">`, with `<p class="aside-title">` when it has a title |
| Fold | `<details class="fold">` with the title in `<summary>` |
| Reference list | `<ol class="references">` with one `<li id="reference-key" value="1">` per cited entry, followed by `<ul class="references uncited">` with one `<li id="reference-key">` per uncited entry |
| Width inside another block | `<div data-width="wide">` |
| Internal link | `<a class="internal-link" href="../../2026-10/rope/#angles" data-target="/2026-10/rope/#angles">`, with the address relative to the page; `data-target` names the entry of `previews` and is missing when the target is an article published from an HTML file. The anchor may name a heading, a paragraph anchor, a sidenote, a reference entry or an equation of the target article. |
| Embed | `<div class="embed">` holding one `<div class="embed-part">` per address, each ending with `<p class="embed-source"><a href="…"><cite>Article title</cite><span class="embed-number">3.2</span></a></p>`; the number is missing for content before the first `##` heading |
| `:::embed` inside embedded or previewed content | One `<p class="embed-link">` per address, holding an internal link whose text is the title of the target heading or article |
| Component | `<figure class="component" data-component="name" data-params="{…}">` with `data-frame="none"` when the component declares `frame: false` and `style="width:560px"` or `style="width:70%"` when a pixel or percent width is set. It holds `<div class="component-box">`, whose `style` sets `--component-height`, `--component-ratio`, `--component-narrow-height` and `--component-narrow-ratio` (`auto` where unused), and a `<figcaption>` when the block has text between its fences. The runtime sets `data-state` on the figure to `loading`, `ready` or `failed` and appends the custom element to the box. |
| Math | `<mjx-container class="MathJax" jax="SVG" data-tex="…">` holding an SVG, with `display="true"` for a display formula. The styles from `mathStyles()` in `src/render/math.js` lay it out. |
| Numbered equation | `id` on the element MathJax generates for the equation number: the label name for a labeled equation and `eq-` plus the number, such as `eq-2`, otherwise |
| Equation reference | `<a class="eqref" href="#label">(1)</a>`, with the label percent-encoded in `href` |
| Code | `<pre class="shiki bake" data-language="python">` with `<span>` colors that use the `--code-…` CSS variables |
| Table | `<div class="table-scroll">` around the `<table>`, so a wide table scrolls horizontally |
| List table | `<div class="table-scroll">` around `<table class="list-table">` with a `<thead>` row and `<tbody>` rows |
| Image | `<img>` with `width`, `height`, `loading="lazy"` and `decoding="async"`; an inline image also has `style` with its width when the article sets a size |
| Figure | `<figure class="figure">` holding the `<img>` and a `<figcaption>`, with `style="width:560px"` when the article sets a size and `data-float="left"` or `data-float="right"` when it sets `float`. The theme makes the image fill the figure and centres the figure in the column. |
| Example | `<div class="example">` holding `<div class="example-source">` with the highlighted Markdown and `<div class="example-result">` with the rendered content |

## Themes

A theme is a folder with three entry files. `page.jsx` default-exports a SolidJS component that returns the whole `<html>` element of an article page; `home.jsx` default-exports a SolidJS component that returns the whole `<html>` element of the homepage; `client.jsx` is the page script of both pages and imports the theme's stylesheets, fonts and other files. Every theme needs `page.jsx` and `client.jsx`. The site theme, `theme` in `bake.config.js`, also needs `home.jsx`; a theme that only articles choose does not. The built-in themes live in `src/themes/`. A blog adds a theme with a folder `themes/<name>/`, and replaces single files of a built-in theme with files of the same relative path in a folder of the same name, such as `themes/essay/header.jsx`; every import inside a theme folder is looked up in the blog's folder first and in the built-in folder second. A theme imports `solid-js` from Bake, so a blog does not install it.

`src/build/theme.js` compiles the site theme and each theme that a published article uses with Vite and `vite-plugin-solid`. The site theme is compiled even when the blog has no articles, because the homepage is always written. `page.jsx` and `home.jsx` are compiled together for the server into one module that exports `render` for article pages and `renderHome` for the homepage, and are rendered to static HTML with Solid's `renderToString`, without hydration. `client.jsx` is compiled into one classic script and one stylesheet, which together with the fonts and images they refer to are written to `dist/assets/` under names that contain a content hash. A theme that cannot be compiled is reported at the file and position of the error, an article that the theme throws on is reported at the article, and a homepage that the site theme throws on is reported at the theme folder. The homepage is written to `dist/index.html`, so a `public/index.html` is reported as a conflict.

The page component receives these props:

| Prop | Contents |
|---|---|
| `site` | `title`, `url`, `language` and `description` from `bake.config.js`; `description` is undefined when it is not set. |
| `article` | `title`, `summary`, `date`, `tags` (a list, empty when not set), `category`, `draft`, `toc` (the table of contents style of the article or the site), `url`, `words` and `content`, the article structure described above. |
| `assets` | `root`, the relative path from the page to the site root such as `../../`; `styles` and `scripts`, the paths of the compiled stylesheet and script relative to the page; `modules`, the paths of the module scripts relative to the page, which is the component runtime when the article uses a component and empty otherwise; `mathStyles`, the MathJax stylesheet when the article has math. |

The homepage component receives these props:

| Prop | Contents |
|---|---|
| `site` | The same as for an article page. |
| `home` | `groupBy` (`category` or `month`), `columns` (3, 4 or 5) and `categories`, the list of `{ id, name, color, desc }` from `bake.config.js` in the order written there. |
| `articles` | The published articles, newest first and by title within a day. Each entry has `title`, `summary`, `date`, `tags` (a list), `category` (the category object from `bake.config.js`, or undefined), `draft`, `url` (relative to the site root, such as `2026-10/rope/`), `preview` (the path of the article's `preview` file relative to the site root, or undefined) and `image` (the article structure's `image` relative to the site root, or undefined; plain HTML pages have none). Markdown articles and plain HTML pages have the same fields. |
| `assets` | `root`, which is `./`, and `styles` and `scripts`, the paths of the compiled stylesheet and script relative to the homepage. |

A `preview` file is an ES module whose default export is a function that receives an empty element covering the card's 16:9 frame, draws the first frame of an animation into it and returns `{ start(), stop() }`. The function is called once for every card that shows the article, so it keeps its state inside the call. Colours come from the theme's CSS variables, so the preview follows dark mode.

### What a theme writes for bake dev

`bake dev` updates an open page without reloading it when only the article body changed. A theme supports this with three attributes and one event, and the same HTML is published by `bake build`:

| Part | Meaning |
|---|---|
| `data-region="name"` | An element whose content comes from the article body, such as the article text, the table of contents or the word count. Each name appears once in the HTML that the theme renders. |
| `data-line="12"` | An element inside a region that shows one part of the article structure, with the `line` of that part: a block, a heading or a sidenote. |
| `bake:content` | The event that `bake dev` dispatches on `document` after it has replaced the content of the regions. |

After a save, the page script of `bake dev` loads the new HTML of the page. When the new page differs from the old one only inside regions, it replaces the children of every element with that `data-region` value, including copies that page scripts made, and dispatches `bake:content`. Otherwise it reloads the page. A page script that keeps references to elements inside a region reads them again on `bake:content`. An element with `data-line` whose HTML is not in the old page counts as changed: it is highlighted, and when it is off screen a notice names the `##` or `###` section of its line. Double-clicking an element with `data-line` opens `vscode://file/<path of the index.md>:<line>:1`. A theme without these attributes still works in `bake dev`; its pages reload on every save.

### The essay theme

`home.jsx` writes the homepage: the site title and description, a bar that stays at the top of the screen with the chips and the switches, and the cards. When the blog has no published articles, the homepage has no bar and shows one line that says there are no posts yet. It renders the grouping by category (when at least one category has a published article) and the grouping by month, and `data-group` on `<html>` selects the one that is shown, so a reader without scripts sees the default grouping, and the category chips still work as links to their groups. `data-columns` on `<html>` sets 3, 4 or 5 card columns from 1000 pixels up; below 1000 pixels the cards fill the width with a minimum width of 290 pixels. Below 600 pixels the chips take a full line of the bar and the switches go on the line below. Titles and summaries break long words so that they stay inside the card. A card shows the article's preview, its first image when it has no preview, or a block in the category colour with the title when it has neither, and its border takes the category colour, or the accent colour when no categories are set, while the pointer rests on it. `page.jsx` writes the document head of an article page, `header.jsx` the masthead, `toc.jsx` the table of contents, `article.jsx` the body and `previews.jsx` one `<template class="bk-preview-template" data-target="…" data-kind="link">` per entry of `previews`, holding the card content, with `data-kind="reference"` and the layout of the citation card for a `reference` entry. Every block of the article structure is wrapped in `<div class="bk-block" data-type="…" data-line="…">`; blocks that can be wider than the text also have `data-width` (`body`, `wide`, `page`, or `auto` when the article sets no width) and the natural width as `--natural-width`. Each sidenote is rendered once, after the top-level block that first refers to it, as `<aside class="bk-sidenote" data-sidenote="1" data-line="…">`, and headings have `data-line` too. An embed is one block with the `data-line` of its `:::embed` line; the embedded content inside it has no `data-line`, because its lines belong to another article. The regions are `article` on `<article class="bk-article">`, `toc` on the list of the table of contents, `words` on the word count, `glyphs` on the hidden MathJax glyphs and `previews` on the `<div class="bk-previews">` that holds the preview templates. UI text comes from `labels.js`, in Chinese when the site language starts with `zh` and in English otherwise. The words around the source line of an embed, such as 出自《…》, are set by `page.jsx` from `labels.js` as the CSS variables `--bk-embed-source-before` and `--bk-embed-source-after`, because that line is part of the HTML Bake generates.

The styles are in `styles/`. `tokens.css` defines every colour as a CSS variable, for the light and the dark theme, and `page.css` defines the column widths as variables for each breakpoint: 1340 pixels and up, 1000 to 1339 pixels, and below 1000 pixels. The page scripts are in `scripts/`, and `client.jsx` starts them:

| Script | What it does |
|---|---|
| `widths.js` | Gives every block with `data-width="auto"` the width `wide` when its content is wider than the text column and the screen has a wide level, and `body` otherwise, and writes the result to `data-resolved` on every block with `data-width`. |
| `notes.js` | From 1000 pixels up, copies each sidenote into the notes column next to the line of its number and moves it below any block that reaches into the column. Below 1000 pixels, a tap on a number opens the sidenote under its block. Hovering a number or a note highlights both. |
| `folds.js` | Animates opening and closing `:::fold` blocks, and opens every fold for printing. |
| `heading-links.jsx` | Copies the link of a heading when its `#` is clicked, and scrolls to the target of an in-page link after opening the folds around it. |
| `preview-card.jsx` | Shows one card for citations and internal links on devices that can hover with a fine pointer: the reference entry of a citation from 1000 pixels up, and the template of an internal link at every width. A citation that points to another article, such as one inside an embed, shows the template of that article's entry. The card appears 300 milliseconds after the pointer rests on a link, below the link and inside the viewport, switches to another link at once while it is shown or within 600 milliseconds after it hid, stays while the pointer is in it and hides 200 milliseconds after the pointer leaves. Keyboard focus on a link shows its card at once, moving the focus away hides it, and Escape hides it. A click on the card of an internal link opens the target. |
| `toc.js`, `drawer.jsx` | Marks the read, current and following entries of the table of contents from 1340 pixels up, and shows the table of contents in a drawer below that width. |
| `home.js` | On the homepage: loads the preview of each card of the visible grouping when the card comes near the screen and keeps the fallback when the preview fails; starts a preview while the pointer rests on its card or the card has focus, and on devices without hover while the card is in the middle tenth of the screen, and stops it while the card is off the screen; never starts one with reduced motion; switches the grouping and the column count and stores them; marks the category chip of the group on screen, and after a click on a chip keeps that chip marked until the scroll to its group ends; and filters the month grouping by tag. |
| `settings.jsx` | The settings panel. Its rows come from `settingRows`; `chooseSetting(name, value)` applies and stores a choice and dispatches `bk:setting` on `document`. |

The reader settings are defined in `settings.js`: each setting has its values and its initial value, the choice is stored in `localStorage` as `bk-<name>`, and an inline script in the head sets `data-<name>` on `<html>` before the first paint. On the homepage the same script also applies the stored grouping and column count, `bk-group` and `bk-columns`, over the defaults that the page writes from `bake.config.js`. The homepage hides its switches and tag chips unless `data-script` is set. The same script sets `data-script` on `<html>`; the styles hide the sidenotes under their blocks only when it is set, so a reader without scripts sees every sidenote under the block that refers to it. Page scripts that change the layout dispatch the `bk:layout` event on `document`, and the scripts that measure the layout listen to it. `widths.js`, `notes.js` and `toc.js` read the blocks, sidenotes and headings again on `bake:content`, `preview-card.jsx` looks up the template of a link each time it shows a card and hides the card on `bake:content`, and the other scripts listen on `.bk-article` or `document` instead of on single elements, so they work on replaced content without changes. `settings.jsx` dispatches `bake:theme` on `document` when the reader chooses another theme and, while the theme setting is `system`, when the system color scheme changes.

The component frame is styled in `blocks.css` like a figure: border, radius and background from the tokens, none of them with `data-frame="none"`, and the caption styled like a figure caption. The placeholder box keeps the declared height at every screen width, `--component-narrow-height` and `--component-narrow-ratio` below 600 pixels, and shows a striped background until `data-state` is `ready`. The custom element inside the box has `display: block` and `height: 100%`, so the frame keeps its height when the component loads. Buttons, labels, inputs and other controls inside a component show the pointer cursor. When `<html>` has no `data-script`, every box shows the text `componentNeedsScript` from `labels.js` in its centre, and a box whose frame has `data-state="failed"` shows `componentFailed`. `page.jsx` passes both texts to the styles as the CSS variables `--bk-component-needs-script` and `--bk-component-failed` on `<body>`, so the HTML that Bake writes for a component stays the same in every theme.

Components own their content, so the essay styles do not reach into the component box. Every rule that styles the article, and the page-wide rules for links, buttons and focus outlines, ends its selector with `:where(:not(.component-box *))`. `:where()` adds no specificity, so the rules keep their order of precedence. The only styles that apply inside the box are inherited properties such as the font and the text colour, the page-wide `box-sizing: border-box`, the selection colour, the pointer cursor on controls, and `display: block` and `height: 100%` on the custom element itself. A new rule in the essay styles whose subject can be an element inside a component needs the same ending.

## Components

A component is an interactive block that a blog writes. `components/` in the blog holds one component per file, `name.js` or `name.jsx`. The file name is both the custom element name and the block name in Markdown, so it uses lowercase letters and digits with at least one `-`, and it cannot be the name of a built-in block such as `list-table`. `components/lib/` holds code and CSS that components share; files there are not components. A component may import `components/lib/`, npm packages from the blog's `package.json`, `solid-js`, which resolves to Bake's own copy, and `bake/math`.

A component module exports three things:

| Export | Contents |
|---|---|
| `params` | The parameters, as `{ name: { label, type, default, … } }`. `label` is the text shown next to the parameter's control, `default` is required and must be a valid value. The types are `number` with optional `min`, `max` and `step`, `text`, `boolean`, `enum` with `options`, a list of strings, and `file`, a path relative to the article folder that must name a file there, such as `grid.json`. `width`, `height`, `id` and `class` are reserved for Bake. A component without parameters may leave `params` out. |
| `layout` | `width`, the width that `auto` resolves to: `body` (the default), `wide`, `page`, a size in pixels such as `560px` or a percentage of the body column up to `100%`. `height`, required, the height of the placeholder: a number of pixels, `{ ratio: 16 / 9 }` (width divided by height) or a function of the converted parameters that returns either. `narrowHeight`, in the same forms, used below 600 pixels of screen width instead of `height`. `frame: false` drops the border and background and keeps the width and the caption. |
| default | A SolidJS function component, which Bake wraps into a custom element and renders with the parameters as reactive props, or a class that extends `HTMLElement`, which reads `this.params`. Bake sets `params` before the element is connected and calls `update()` when they change. |

An article writes a component as a block, `:::act-fn-plot{fn=gelu range=6 width=560px height=420}`, with the caption between the fences; the caption may be empty. The attributes are converted to the declared types: a bare attribute such as `{toggle}` is `true`, a number must be a number within `min` and `max`, a boolean `true` or `false`, an enum one of its options. An unknown attribute, a value of the wrong type or out of range, and a file that is not in the article folder are reported at the attribute's column. Parameters the article does not set get their defaults, so the component always receives every parameter. `width` takes `body`, `wide`, `page`, `auto`, pixels or a percentage up to `100%`; `auto` or no width uses `layout.width`. `body`, `wide` or `page` gives the block that `width`. A percentage gives the block the width `body` and the frame that share of the body column. A pixel width gives the block `naturalWidth`, so the theme places it like a figure with a pixel width, and the frame that width; the frame is centred and never wider than its column or the screen. `height=420` is a number of pixels that replaces both `layout.height` and `layout.narrowHeight`. `:::{width=…}` around a component, `float` on a component and an `#id` or `.class` on a component are errors. A `file` parameter, such as `points=glu-points.json`, receives the path as written, and the build publishes the file with the article, so the component can fetch it relative to the page. `layout.height` functions run at build time with the converted parameters. Components inside other blocks, such as `:::example` and `:::fold`, are checked and rendered the same way.

Bake reads `params` and `layout` in Node with Vite before it parses the articles, so a component module must not use a browser API such as `window`, `document`, `navigator`, `location`, `localStorage`, `customElements`, `matchMedia`, `getComputedStyle`, `requestAnimationFrame`, `ResizeObserver` or `IntersectionObserver` at the top level, also not in the files it imports from `components/lib/`. Such a use is reported at its position, for example `components/lib/size.js:3:23 lib-plot: components/lib-plot.js uses the browser API window at the top level; the build reads params and layout in Node, so use it inside the component code`. `class … extends HTMLElement` at the top level works, because `HTMLElement` is defined while the module is read. Problems in `params` and `layout` and a missing default export are reported at the start of the component file, prefixed with the component name.

`src/components/bundle.js` builds the components that published articles use in one Vite build: the runtime `src/components/runtime.js` as the entry and one chunk per component that the runtime imports when it needs it, with shared chunks for `components/lib/`, `solid-js` and MathJax, whose chunk is named `mathjax-[hash].js`, and one stylesheet per chunk that loads with it. The files are written to `dist/assets/` under names that contain a content hash. A page with components loads the runtime as a module script; a page without components loads nothing. The runtime finds the frames on the page, and again on `bake:content` after `bake dev` replaced the article, and starts a component when its frame comes within 800 pixels of the viewport, and every component before printing: it loads the component's chunk, defines the custom element once, creates the element, sets `params`, appends it to the box and sets `data-state="ready"` on the frame. When the chunk cannot be loaded, or the constructor, the `params` setter or `connectedCallback` throws while the runtime creates and appends the element, the runtime removes the element, sets `data-state="failed"` and logs the error to the console. The browser reports an exception from a custom element callback as an `error` event on `window` and `append` returns normally, so the runtime listens for that event while it appends. Without scripts the page shows the frame, the placeholder and the caption.

Themes dispatch `bake:theme` on `document` when the colors of the page change. A component that draws with canvas or WebGL redraws on it.

`bake/math` exports `texToSvg(tex, { display = false } = {})`, which returns a promise of an `<svg>` element. It typesets the formula with MathJax 4 in the browser, with the TeX packages and the New Computer Modern font that `src/render/math.js` uses and with the macros of the blog's `preamble.sty`. The font keeps less common glyphs, such as double-struck letters, in separate files that MathJax loads when a formula needs them, which is why the function is asynchronous. A TeX error rejects the promise. MathJax is part of the component bundle only when a component imports `bake/math`, and a page downloads it only when one of its components does.

A component's own CSS, including CSS in `components/lib/`, uses class names that start with the component's prefix, such as `act-` for `act-fn-plot`, so that components on the same page and the theme do not style each other.

## bake dev

`src/build/site.js` holds the steps that `bake build` and `bake dev` share. `createSite(root, { drafts })` creates the state of one blog, where `drafts` set to true gives drafts a page and a card on the homepage, and `updateSite(site, changedPaths)` reads it and renders every page: with `null` it reads everything, with a list of changed paths relative to the blog root it reads `bake.config.js`, `preamble.sty` and the components again only when one of them or a file in `themes/` or `components/` changed, parses again every article after that and otherwise only the articles whose folder contains a changed path, compiles a theme again only when a file in `themes/` changed or when the theme becomes or stops being the site theme, because only the site theme is compiled with `home.jsx`, and bundles the components again when they were read again or when the set of components that published articles use changed. After reading, it links every article again, parsed again or not, because link errors, preview cards and embedded sections depend on other articles; linking and building the article structure take much less time than parsing. It returns the sorted errors, the articles, the pages with their outputs, the homepage output, the asset files of the themes and the components, and the files of `public/`. `bake build` calls it once with `null` and writes the outputs with `writeDist`; `bake dev` keeps the state and calls it after every save.

`src/dev/watch.js` watches the blog root with `fs.watch` and `recursive: true`, ignores `dist/`, `node_modules/` and every file or folder whose name starts with a dot, and collects the paths of one save for 40 milliseconds. A path that does not exist and was not a known file before, such as a temporary file an editor writes and deletes during a save, is ignored. When the blog root can no longer be watched, because it was removed or the system has no file watches left, `bake dev` closes the server, prints `bake dev: cannot watch <root>: <reason>` and exits with status 1. `bake dev` does not reload the modules that `bake.config.js` imports; restart it after changing them.

`src/dev/preview.js` keeps the pages and the homepage that `bake dev` serves, in memory. When the errors include a file that is not an article, such as `bake.config.js` or a theme file, it keeps every page. Otherwise it takes the new pages of the articles without errors and keeps the last pages of the articles with errors. It compares the old and new pages: a page whose front matter changed, or that appeared or disappeared, is reloaded; a page whose HTML changed is updated in place; the homepage is reloaded when its HTML changed, which happens when the front matter of an article changes or an article appears or disappears; and a changed path that is not an article's `index.md` reloads every page.

`src/dev/server.js` serves the pages and the homepage at `/` with Node's `http` module on port 4321 or the next free port, on every network interface. It adds `<script src="/__bake/client.js" data-bake-dev>` at the end of the body of every HTML page; on an article page the script carries the path of the `index.md` for VS Code, its path in the blog and the outline of `##` and `###` headings with their lines. `/__bake/events` is a Server-Sent Events stream with three events: `hello` with an id that changes when `bake dev` restarts, `problems` with the current problems, and `update` with the addresses to reload (`reload`, a list or `"all"`) and the addresses to update in place (`refresh`). Any address without a page answers 404 with the list of every article. `src/dev/client.js` is the page script: it keeps the HTML the page was loaded from, applies updates as described in "What a theme writes for bake dev", stores the scroll position in `sessionStorage` before a reload and restores it after, and shows the problems list and the notice in a shadow root styled by `src/dev/client.css`. The problems list opens when problems appear and closes when they are fixed. While the list is closed, a dot in the bottom right corner of the page takes its place: it is small and grey when there are no problems and red with the number of problems otherwise, and clicking it opens the list. The list, the dot and the notice fade and slide in and out with CSS transitions; when the reader prefers reduced motion, they only fade.

## Error reports

Every problem Bake finds in a blog is reported as one line:

```
content/posts/llm/rope/index.md:3:7 URL /2026-10/rope/ is already used by content/posts/2026-10/rope/index.md
```

The format is `file:line:col message`, with the path relative to the blog root and the message in English. Bake runs every check before it reports, so one run lists all problems, sorted by file, line and column, followed by a count such as `1 error, dist/ was not written`. Articles are checked against the settings in `bake.config.js`, so when `bake.config.js` has errors, Bake reports those and does not check the articles. A build with errors writes nothing and leaves an existing `dist/` unchanged. A build without errors writes into `.dist-staging/` in the blog root and then replaces `dist/` with it, so `dist/` never holds a partly written site or files from an earlier build. Every build first removes `.dist-staging/` and `.dist-previous/` left by an interrupted build. `bake dev` shows the same lines in the terminal and on the page.

## Libraries

- Use mature libraries for general problems: Markdown parsing, math typesetting, syntax highlighting, diffing, sanitizing and validation.
- Write Bake's own core pieces by hand: the article structure, the theme interface, the component contract and the dev server's page updates.
- When switching to a library, accept its native behavior. Do not wrap it to reproduce the quirks of the code it replaces.
- Add a dependency only in the change that uses it, and pin the npm major version given in `package.json` when regenerating the lock file.
- Markdown is parsed by remark with GFM, math, front matter and `remark-cjk-friendly`, which lets emphasis close next to Chinese punctuation. Bake's own syntax is written as micromark extensions in `src/markdown/`: `\eqref{label}` in text, `:::` blocks (remark-directive does not accept a block without a name such as `:::{width=wide}`, and its text directives would read `\eqref{eq:ffn}` as a directive), `==highlight==` with the same CJK rules that `remark-cjk-friendly-gfm-strikethrough` uses for `~~`, `[@key]` citations, and footnote references without a definition, which GFM would otherwise leave as plain text. Before parsing, `src/markdown/table-math.js` replaces each `|` inside `$…$` on a table line with a private-use character and restores it afterwards, because GFM splits cells before it reads math.
- Math is typeset by MathJax 4 (`@mathjax/src`) into SVG with the New Computer Modern font. Each article is typeset in its own MathJax document, so macros defined in one article do not reach another, and every formula is compiled twice so that `\eqref` can refer to a later label.
- Code is highlighted by Shiki with a theme created by `createCssVariablesTheme`, so the colors are CSS variables that themes and dark mode set.
- Images are read and converted by sharp. Size values such as `560px` and `70%` are parsed by `parseSize` and checked by `sizeProblem` in `src/config/rules.js`, which every syntax with a pixel or percent size uses.
- Themes are compiled by Vite with `vite-plugin-solid`, and their page structure and page scripts are written with SolidJS.
- The essay theme self-hosts LXGW WenKai from `lxgw-wenkai-webfont`, whose stylesheet splits the font into files by character range so that a page only downloads the files for the characters it shows, and JetBrains Mono from `@fontsource/jetbrains-mono`.
- Browser tests use Playwright, pinned to the exact version that matches the Chromium preinstalled in the cloud environment.
- `bake dev` uses Node's `http` module, Server-Sent Events and `fs.watch` with `recursive: true`, and needs no dependency of its own.

## Clean code

- The only compatibility code allowed is one migration step that upgrades old data files to the current format. There are no shims, fallbacks, legacy aliases or dual code paths.
- Fix root causes and replace old behavior outright. Code that is no longer used is deleted; git history keeps it.
- A known performance gap is written down here together with who accepted it.
